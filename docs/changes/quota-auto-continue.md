# V0.quota-auto-continue: auto-continue quota-stopped threads at reset, fall back to notice resets, and guard rapid duplicate sends

→ V0.quota-wait (quota stops wait for the reset), V0.quota-wait-midturn (mid-turn detection, snooze and settle-when-done), V0.quota-reset-wake (quota wakes and `WhenQuota`). *Amends V0.quota-wait (2, 4, 5) and V0.quota-reset-wake (1, 2, 4).*

When a quota-stopped thread's parsed reset time passed, `QuotaWaitText` returned empty and `Attention` dropped the thread straight into **Failed** in Needs you with the hours-old `"Resets in …"` message instead of continuing the thread. In addition, `thread.wakeOnQuota` and `mcp__fyr__watch {when: {kind: "quota"}}` could not resolve providers without `quota.Service` polling even when the thread's own quota notice named a future reset time, and neither the desktop nor the phone composer guarded against rapid duplicate `thread.send` submissions while a send was in flight.

1. **Auto-continue at quota reset.** A thread stopped with `core.ClassQuota` whose notice names a reset time (`core.QuotaReset`) waits until `QuotaReset + 15 s` (`QuotaResumeBuffer`, so the provider's quota clock has rolled over) and then automatically continues on `KindClock` through the state machine and agent feed: Fyr clears `Failure`, sets `Starting`, increments `QuotaResumes` and `QuotaResumedAt`, records `quota.continued`, and queues a waking `[Fyr]` notice (`EffectFeed`) telling the agent that quota has reset and to continue where it left off. While waiting (including during the 15 s buffer and until `KindClock` runs), the thread stays **Waiting** in Working rather than flipping to **Failed**; `Engine.Tick` runs `KindClock` for due threads before checking time-driven attention transitions so a due reset never broadcasts a transient **Failed** state.
2. **Loop protection and non-stale failure reasons.** Consecutive automatic continues are bounded to `MaxQuotaAutoResumes = 3`. If the provider immediately rejects with `ClassQuota` again within `2 min` (`QuotaQuickFail`) of the previous auto-continue, the next auto-continue enforces a minimum backoff (`1 min`, then `5 min`) even if the notice names a shorter duration. Any run that finishes without a quota failure, or any owner move (`thread.send`, `thread.retry`, `thread.dismiss`, `thread.settle`, `thread.wakeOnQuota`, `handover.done`), resets `QuotaResumes` and `QuotaResumedAt`. Once `QuotaResumes` reaches the bound (or if a quota failure otherwise surfaces as **Failed**), Fyr stops auto-continuing and moves the thread to **Failed** in Needs you with a clear non-stale reason (never re-displaying an expired relative `"Resets in …"` countdown).
3. **Lifecycle, snooze and settle interaction.** Settled, archived, running, starting, handing-over, open-decision, or outbox-pending threads never auto-continue. Unarchiving a thread whose quota reset already passed surfaces the failure for the owner instead of launching a surprise run. A quota wait and its auto-continue transition preserve both "Snooze until work is done" (`V0.185`) and "Settle when done" (`V0.203`); if loop protection stops auto-continuing, snoozes wake to **Failed** and "Settle when done" is dropped.
4. **Notice-based `wakeOnQuota` and `WhenQuota` fallback.** When `quota.Service.ResetOf` is unavailable or returns an error for a provider and no specific window was named, both `thread.wakeOnQuota` and `mcp__fyr__watch {when: {kind: "quota"}}` fall back to the thread's own parsed `core.QuotaReset(t.Failure)` when the thread matches that provider, is quota-stopped, and the reset time is in the future. Stale or past notices, missing times, different providers, and explicitly named unknown windows are still refused.
5. **Client in-flight send guard and deduplication (desktop and phone in sync).** Both `Composer` (desktop) and `MComposer` (phone) share a synchronous submit guard (`createSubmitGuard`) that blocks re-entrant sends until the in-flight request settles and disables the Send button while sending; the desktop composer also ignores `KeyboardEvent.repeat` on Enter. `useThreadCommands.send` deduplicates concurrent identical in-flight `thread.send` calls per thread so rapid taps or key repeats cannot emit multiple commands with distinct `commandId`s.
