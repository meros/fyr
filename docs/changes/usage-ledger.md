# V0.usage-ledger: each result's tokens go to a usage ledger per host, and the thread header shows the thread's total

→ Decision 0041 (phase 1), SPEC 3 ("Outside the one path", item 4) and the new 3.18. Fyr kept no count of tokens: the result of a turn kept only its duration, the trimmed `msg` events drop `usage`, and a subagent's count was shown on its task row and kept nowhere.

(1) **What the CLI says, proved on recorded protocol logs.** `result.modelUsage` counts every model of the session, the CLI's own small-model calls and the subagents among them, and keeps counting across a process that resumes the session. `result.usage` is the main agent's requests of this turn only. The usage on an assistant line is the request's as at its start: its output count is partial. So the totals come from `modelUsage`, diffed per session.

(2) **The meter** (`internal/usage`). `Fold` diffs a cumulative report against the session's baseline; a count that went down, or a main model that grew by less than the main agent's own share of the turn, is a reset (a session copied to another account or host starts again from zero under its id). `Split` gives each model's delta its `main` and `other` parts. `Meter.Record` writes a report's rows and the next baseline in one transaction (`store.RecordUsage`), and refuses a report id it has seen, so a result the runner delivers again after a restart of fyrd counts once. It keeps each thread's total in memory, read from the ledger at start.

(3) **The ledger** (`store/usage.go`): `usage` (one row per report, model and part, with its dimensions copied in), `usage_seen` and `usage_baseline`, created with the schema. `UsageRollup` sums it by any of its keys, with a day range and filters.

(4) **The agent.** `cli.UsageReader` reads a result in one shape; claude's reads `modelUsage` and `usage`. Every result is metered, a stray one outside a turn too. A turn's trigger is what started it: the owner's message, another thread's, a press in the live view, a handover, the feed's notices (a wake when one of them is a Rule's), or the CLI by itself (background); a queued message gives its trigger to the turn the CLI starts it in. The main model is the one the CLI's init names, else the session's biggest. The account is the provider's quota identity (V0.44: two providers on one login are one account), hashed so no login folder reaches a client; billing is `subscription` for a CLI login, `api-key` or `endpoint` for a key.

(5) **The thread total.** The meter tells the engine a thread's new total right after it wrote a report (`Engine.SetThreadUsage`, outside `e.mu`: V0.182 forbids a dependency call under it), before the agent reports the run's end, so that apply's DTO carries it; at start it gives the engine every total it loaded. The thread DTO carries `usage` (input, output, thinking, cache read, cache write 5 min and 1 h, and their plain sum `total`). The desktop header and the phone header show it as one chip after the agent pill (`UsageChip`, shared), with each kind in its title. Tokens only, by the owner's answer to the decision's question 4.

Tests: `internal/engine/usage_test.go` (TestThreadUsageInTheDTO), `internal/usage/usage_test.go` (TestFold, TestSplit, TestRecordReplayAndRestart, TestSeed), `internal/cli/claudecli/usage_test.go`, `internal/agent/usage_test.go` (TestResultUsageReachesTheLedger, TestTriggerOfAQueuedMessage, TestTriggers), `web/test/usage.test.ts`; the layout test runs with a usage chip on every mock thread.
