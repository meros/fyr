# V0.host-updates: Settings → Hosts shows how far each host is from the newest release, and a held-back release can be retried

→ V0.126, V0.153 (decision 0027), #154 (each host updates on its own; the decision issue #144, option 4: no canary). A host that stopped updating went unnoticed.

1. **Each host says where it is.** A host with a release source sends its update state in its state and as the stream frame `update` (docs/API-v0.md): the commit it runs, the commit `deployable` points at, how many commits behind it is, its last update (result, reason, time), the release it holds back and whether a local build pauses auto-update. A front carries it on the host's row (`hosts[].update`), so every front shows every host's.
2. **Behind costs one call per move.** The watcher counts the commits between what runs and `deployable` with one GitHub compare when either moves, and keeps the count; 0 when the host runs the wanted release, without a call.
3. **Settings → Hosts.** A host's row adds "3 commits behind · last update failed", "holds back c705ef5", "up to date" or "local build" to its line; a row whose host holds a release back, or whose last update failed while it is behind, is marked as a bad row. The host's page has an Updates group: Runs, Newest release (and how far ahead), Last update, and the held-back release in the group's foot. One component on the desktop and the phone; the phone's sizes come from the same `.set.phone` rules as every settings row.
4. **Update now · retry.** While a release is held back the button on the host's page and in Automation → Updates reads "Update now · retry". The press (`host.updateNow`) clears the mark and installs the newest release; if it fails again it is marked again. A release that goes live clears the mark too. A mark shows only while `deployable` still points at its release.
5. **Smoke failures count.** A release whose smoke test fails on a host is marked bad there, as one that rolled back is, so the next read of `deployable` does not download and fail it again.
6. **Two installs side by side** (decision 0021): a test runs two installs with their own data folders through the watcher: each downloads into its own `builds/`, keeps its own kv, and a release that fails on one is held back there only.
