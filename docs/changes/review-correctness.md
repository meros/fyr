# V0.review-correctness: a PR's checks and review follow its current head, a thread is filed by its reduce, the owner's mark on a host record is stored with its receipt, every staged thread passes the thread invariants, a suspended quota wake follows its reset, and the engine's clock drives deploy state and revs

→ V0.55, V0.58 (filing), V0.98 (4) and V0.101 (the owner's Done and Abandon on a host record), V0.136 (a head change), V0.quota-reset-wake, V0.thread-invariants, decision 0020 (one transaction per command).

(1) **A PR's checks and review are what GitHub says of its head.** A PR read with no checks (`none`: GitHub lists none yet on a new head, or the repo has no CI) or with no review decision (dismissed, or not required) left the conditions of the earlier read in place, and a new head dropped only the refused merge. So "CI failed" kept blocking a push that fixed it, while the annotations of the failure were already gone. Now `none` drops the checks condition, an empty decision drops the review condition, and a new head drops both before the read sets them again. Only conditions Fyr read go: what the owner or an agent set stays.

(2) **The reduce files the thread.** The engine filed a thread into the project whose folder covers it after the reduce (`assignProject`), outside the reducer, so the rules and the invariants of that reduce never saw it, and a replay could not reproduce it; a project command used a second copy of the rule (`refiled`). Now `core.Filed` is the one rule, and `core.ReduceIn(core.Env{Projects}, ...)` applies it in every reduce before the rules run. `Reduce` without an Env leaves the filing as it is (tests). A project command stages `project.matched` with `core.Filed`'s answer; the load pass uses it too. The trans-host handover still files the new thread by hand in its own code; it should send the project through the handover's Input and let the reduce file it.

(3) **The owner's Done or Abandon on a host record is one transaction with its receipt.** It checked the receipt, applied, then wrote the receipt in a second transaction with no lock across them: two sends of one command both applied (the second one got "already abandoned"), and a crash between the steps left the record moved without a receipt. Now the record's path takes the command id: it replays a receipt and writes the new one in the record's transaction, under the engine's lock. The threads that show the record take its `change.observed` as an observation whoever moved it; with the owner's source they refused it.

(4) **Every staged thread passes the thread invariants.** Only the thread path checked them; the threads that a project command (`project.matched`, the follow-up Inputs) or a host record (`change.observed`) staged were never checked. All three paths now check each committed thread the same way (`threadChecks`).

(5) **A suspended quota wake follows its reset.** `quota.sync` moved only armed rules, so a wake suspended while the thread was settled resumed with the earlier reset and fired before the quota was back. It now moves every rule.

(6) **The engine's clock.** The deploy state's end time, the revs and the screenshot limit read `time.Now` instead of `e.Now`, so a sim's fake clock did not drive them.
