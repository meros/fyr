# V0.thread-issues: a thread links the GitHub issues its work is about, and shows them beside its PRs

→ 13.5 (Header), V0.multi-pr. A thread showed the PRs its work opened, but not the issue the work was for: the owner had to open the PR to see which issue it closed, and an issue the agent filed for a follow-up was only a URL somewhere in the conversation.

1. **Linked issues.** A thread keeps `issues` (at most 20): each with its URL, repo, number, title and state as Fyr last read them (`OPEN`, `CLOSED`, or none before the first read), how it joined (`via`) and, for one a PR closes, that PR. The first way an issue joined is kept; later reads update its title and state.
2. **How an issue joins.** (a) `pr`: a PR of the thread closes it: the poller's batched PR query reads GitHub's closing references (`Closes #N` in the PR's body, or a link made on GitHub), up to 10 per PR, with their title and state. The single `gh pr view` read cannot see them and leaves the links as they are; a link never goes away because a read did not see it. A dismissed PR links nothing. (b) `created`: the agent runs `gh issue create` and the issue URL is printed on a line of its own (as `gh pr create`'s PR, V0.8); `gh issue view` links nothing. (c) `owner`: the owner's message (New thread or a send) holds an issue URL. Another agent's message does not link. (d) `agent`: the agent calls the MCP tool `issue_link {issue, unlink?}` with the issue's URL; `unlink: true` removes a link that was wrong. A PR URL is refused.
3. **Reads.** The poller reads the linked issues that are not closed, of threads that are not settled or archived: the issues of one repo in one GraphQL query (up to 20), each at most every 10 minutes, one never read at the next poll. It reports an issue only when its title or state changed (`issue.observed`, which does not move the thread's `updatedAt`). A closed issue is not read again.
4. **Header (desktop and phone).** After the PR chips, one chip per linked issue, open ones first: `issue #12`, or `issue #12 closed` in the done colour; with the short repo name first when the header's PRs and issues span more than one repo. The tooltip says the repo and number, the state, the title and why it is linked. A click or tap opens the issue on GitHub in a new tab; on the phone each chip is a 44 px tap target, as the PR chips are. Nothing appears by itself in a place the owner types: a new link adds a chip to the header and takes no focus.
