# V0.host-ids: the host order is kept by install id, settings reads go as the browser, a host with no id says it needs an update, and each host has its own stored state

→ decision 0031 (2.1, 2.5, 2.7, C7, F17, 4.3), V0.124, V0.127, V0.132, V0.172 (5), V0.177 (3), V0.client-refs, #372. *Amends V0.132 (5) (the order is kept by id beside the names), V0.172 (5) (the host order no longer stays by name inside the front), V0.125 (a host row with no id says "needs an update", not "no id").* (decision 0031, #277)

(1) **The host order by id.** `front.hostOrder {ids}` keeps the hosts by install id and by name. The front writes both to every host (`host.hostOrder {names, ids, at}`; the host keeps `ids` beside `names` and sends both on its stream) and ranks `hosts[]` by id. A host that is renamed in a front's config keeps its place. An order set before this change has only names and still ranks by name. A host with no id yet is ranked by its name. When the order names such a host, it is kept by names alone, so it stays whole. A host older than this change ignores `ids` and keeps the names, as before. The old route's `front.hostOrder {names}` stores the ids the front knows for those names. **The pins stay by name.** A pin records which id the front first saw under a host's name (V0.124), and that is what the name is for: it says when another install answers under it. A pin is also what turns a name into an id here (decision 0031 4.3).

(2) **Settings reads go as the browser.** The six settings reads (V0.127) on `/api/h/<id>/` are read by the front so it can keep the last answer for an offline host. They now carry the browser's `Fyr-Actor` (the device and the owner, with `Fyr-Origin`), as every other forwarded call does, not the install's own (decision 0031 2.7). The kept answer is served as before.

(3) **A host with no install id** (older than V0.124) is listed in Settings → Providers and Automation with the line "Needs an update" and the note "<host> runs a Fyr from before install ids, so its settings cannot be read or changed from here. They show once it has updated." Nothing is read from it or sent to it, because no call can name it. Its Settings → Hosts row ends in "needs an update". It is the same part and the same row on the desktop and the phone.

(4) **Each host has its own stored state.** The device keeps each host's state as that host last sent it, by install id (IndexedDB `host:<id>`). A host is asked `?since=` its own newest rev from that state, and its partial answer merges into that state before the hosts are flattened into one. One host's clock or records never decide what is asked of another, and the merge no longer reads the whole stored state. A rotated id (V0.client-refs (4)) moves the host's stored state with its timelines. The whole state the app draws at once on start (V0.38) is kept as before. The first start after the update reads each host's whole state once.

(5) **Tests.** `internal/front/hostorder_test.go` (TestHostOrderIsKeptByIDAcrossARename: the order set by ids is kept on both hosts with names and ids, and a front whose config renames b still shows it first; TestHostOrderByNameStillRanks); `internal/front/hop_test.go` (the six settings reads on the prefix reach the host as the device); `web/test/cache.test.ts` (each host is asked since its own rev, and its delta lands in its own state); `web/test/host-settings.test.ts`, `web/test/hosts.test.ts` (the host with no id); `web/test/layout.e2e.mjs` (desktop and phone: old-nuc's part says "Needs an update" with the note and shows no providers; its Hosts row ends in "needs an update").
