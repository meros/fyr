# V0.freeze-fast-class-name: after the PSI trigger, with the agents' memory stalling critically, the guard freezes the work that grows without waiting the detector's window; a learned heavy class is named after the command that did the work, never a filter

→ decision 0036 (B) (act before oomd) and E5 (triggers, not a tick), V0.164 sections 4.6 and 7, V0.209, V0.guard-agents-stall, V0.guard-wake. Builds on V0.psi-trigger-slice.

(1) **The cause, freeze.** On 20 Nov the owner's desktop froze. `daemon.log` has `guard: PSI trigger: the agents' memory stall crossed 150 ms in 2 s` at 07:32:12 and `froze undeclared work … episode_age=45s … agents_stall=critical unit_full=10%` only at 07:33:01, 49 s later, with no guard line between them. Undeclared work becomes a flag, and so something the guard may freeze, only after the detector's window W (45 s) of readings over the threshold (V0.164). Work that starts growing when the stall starts can therefore not be frozen for 45 s, however hard the agents stall. On 20 Nov the work had been flagged since 07:32:16, and memory counted as short only at 07:33:01, when the agents' avg10 stall read critical. So this change does not remove all of that minute: the trigger does not make memory short by itself.

(2) **Freeze fast.** When the PSI trigger fired less than `TriggerFresh` (20 s, two ticks) ago and the agents' stall is critical, or the unit's stall is near oomd's limit (V0.guard-agents-stall (3)), and no flagged work could be frozen, the guard asks the detector to flag at once the thread that is neither admitted nor flagged and whose working set at the last reading is furthest above its idle level, if that is over the memory threshold (8 % of the agents' memory). Then the usual freeze decides. Services are never frozen, the work must hold its share of the thread's memory, MaxFreezes, someone else must gain, at most the running threads less one are frozen, and the next freeze waits `AddFreezeAfter` unless near oomd's limit. The early flag is an episode like any other: it goes on with the readings and ends when the work is calm for the window. The log says `guard: flagged thread=… without the window: the PSI trigger fired and …`. With no trigger, or with an older trigger, or with an elevated stall only, the window still holds.

(3) **The cause, class name.** A command learned from undeclared episodes (V0.209) was the program and first argument of the line's *last* segment that was not trivial. `go test ./... | cut -c1-100` taught the class "cut". At 07:33:08 fyrd's gate hook held a diagnostic `tail … | grep … | cut …` as a heavy job: `held at the gate … class="cut" admitted=true learned=true: memory is short`. In the same way `scripts/ci-local.sh 2>&1 | tail -8` would have taught `scripts/ci-local.sh 2>&1`, with the redirection taken for an argument.

(4) **The command that does the work.** Filters and bare wrappers are trivial too: `cut`, `sed`, `awk`, `wc`, `sort`, `uniq`, `tee`, `tr`, `less`, `more`, `column`, `jq`, `egrep`, `fgrep`, `time`, `timeout`, `nice`, `ionice`, `env` (with `tail`, `head`, `grep`, `rg`, `cat`, `echo`, `true`, `sleep`, `cd`, `export` as before). `ionice` and `nice -19` are stripped as wrappers, as `nice -n`, `env`, `timeout`, `sh -c` and `nix develop -c` already were, so the command inside is read. A redirection (`2>&1`, `>log`) ends the arguments. A line of filters alone (`tail -f x | grep y | cut -c1-80`) teaches nothing.

(5) **What was learned before.** When the book is read at start, a learned pattern whose program is trivial is dropped and logged once: `heavy: dropped the learned class "cut": a filter or wrapper, not the command that did the work`. It is not marked as removed by the owner, so the command that did the work can be learned. A suggestion whose program is trivial is dropped too.
