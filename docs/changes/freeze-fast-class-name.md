# V0.freeze-fast-class-name: a fresh PSI trigger, now set at the critical level, is a critical agents' stall for 20 s and the guard freezes the work that grows without waiting the detector's window; a learned heavy class is named after the command that did the work, never a filter

→ decision 0036 (B) (act before oomd) and E5 (triggers, not a tick), V0.164 sections 4.6 and 7, V0.209, V0.guard-agents-stall, V0.guard-wake. Builds on V0.psi-trigger-slice. *Amends V0.guard-wake (4): the trigger is `full 200000 2000000`, it was 150 ms.*

(1) **The cause, freeze.** On 20 Nov the owner's desktop froze. `daemon.log` has `guard: PSI trigger: the agents' memory stall crossed 150 ms in 2 s` at 07:32:12 and `froze undeclared work … episode_age=45s … agents_stall=critical unit_full=10%` only at 07:33:01, 49 s later. The work had been flagged since 07:32:16, but memory counted as short only at 07:33:01, when the agents' avg10 stall first read critical (10 %). avg10 is a 10 s average, read on a 10 s tick, so it lags the stall the trigger reports by tens of seconds. The trigger made the guard run, and the guard found memory not short (headroom 64 %, avg10 elevated) and did nothing. Besides, undeclared work becomes a flag, and so something the guard may freeze, only after the detector's window W (45 s) of readings over the threshold (V0.164): work that starts growing when the stall starts cannot be frozen for 45 s.

(2) **fyrd was not starved.** Between 07:32:12 and 07:33:01 fyrd logged no guard line because nothing changed: the guard logs "memory short" only when the state changes, the 10 s tick logs nothing while memory is not short, and the trigger's own line is said at most once a minute (the next is at 07:33:13). Its once-a-minute `budget over` line came on time at 07:32:51, there is no `stall:` line of the lock watchdog, and fyr.service's own `memory.pressure` holds 1.5 s of full stall since boot. Nothing in `nix/module.nix` changes.

(3) **The trigger is the critical level.** fyrd's trigger is now `full 200000 2000000`, 200 ms of full stall in 2 s, 10 %, which is the critical level of avg10, so a trigger and "critical" mean the same thing. For `TriggerFresh` (20 s, two ticks) after a firing, the sampler's signals read the agents' stall as critical, whatever avg10 says. Admission's hold ("the agents' memory stalls (critical)"), the guard's "memory short" and the budget all read those signals. `freezeGuard` applies the same rule to its own signals. The guard's lines add `psi_trigger=fresh`. The trigger's log line says `crossed 200 ms in 2 s (critical)`.

(4) **Freeze fast.** Within `TriggerFresh` of the trigger, when no flagged work could be frozen, the guard asks the detector to flag at once the thread whose working set at the last reading is furthest above its idle level, if that is over the memory threshold (8 % of the agents' memory). Threads that are admitted or already flagged are skipped. Then the usual freeze decides. Services are never frozen, the work must hold its share of the thread's memory, MaxFreezes, someone else must gain, at most the running threads less one are frozen, and the next freeze waits `AddFreezeAfter` unless near oomd's limit. The early flag is an episode like any other: it goes on with the readings and ends when the work is calm for the window. The log says `guard: flagged thread=… without the window: the PSI trigger fired … ago`. Without a trigger in the last 20 s the window still holds. On 20 Nov the work would have been frozen at 07:32:12 if it was over the threshold then, and at the latest with its flag at 07:32:16.

(5) **The cause, class name.** A command learned from undeclared episodes (V0.209) was the program and first argument of the line's *last* segment that was not trivial. `go test ./... | cut -c1-100` taught the class "cut". At 07:33:08 fyrd's gate hook held a diagnostic `tail … | grep … | cut …` as a heavy job: `held at the gate … class="cut" admitted=true learned=true: memory is short`. In the same way `scripts/ci-local.sh 2>&1 | tail -8` would have taught `scripts/ci-local.sh 2>&1`, with the redirection taken for an argument.

(6) **The command that does the work.** Filters and bare wrappers are trivial too: `cut`, `sed`, `awk`, `wc`, `sort`, `uniq`, `tee`, `tr`, `less`, `more`, `column`, `jq`, `egrep`, `fgrep`, `time`, `timeout`, `nice`, `ionice`, `env` (with `tail`, `head`, `grep`, `rg`, `cat`, `echo`, `true`, `sleep`, `cd`, `export` as before). `ionice` and `nice -19` are stripped as wrappers, as `nice -n`, `env`, `timeout`, `sh -c` and `nix develop -c` already were, so the command inside is read. A redirection (`2>&1`, `>log`) ends the arguments. A line of filters alone (`tail -f x | grep y | cut -c1-80`) teaches nothing.

(7) **What was learned before.** When the book is read at start, a learned pattern whose program is trivial is dropped and logged once: `heavy: dropped the learned class "cut": a filter or wrapper, not the command that did the work`. It is not marked as removed by the owner, so the command that did the work can be learned. A suggestion whose program is trivial is dropped too.
