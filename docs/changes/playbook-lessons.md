# V0.playbook-lessons: an agent the owner corrected suggests a lesson for the project; once the owner takes it, every later agent there is told it

→ V0.project-playbook, V0.playbook-moments, 3.15, 5.12. *Amends V0.project-playbook (1) (a seventh slot, named like a stage) and V0.playbook-moments (4) (Take makes the entry the owner's).*

Why: a correction lasts as long as the thread it was given in. The owner writes "no, run the e2e tests too", the agent does, the thread settles, and the next agent in the project can make the same mistake. The playbook's slots hold the path of a change (stages, verify, promote, issue, run, rollback), not "what keeps going wrong here", and an agent's prompt line said to record only how the project works.

What the research on self-improving agents says, and how it shaped this change (each result is its authors' own; most are preprints):

- **Keep the context as separate items and edit one at a time, never rewrite it whole.** ACE ([arXiv 2510.04618](https://arxiv.org/abs/2510.04618), ICLR 2026) grows an agent's context as a playbook of items, edits them one at a time with small updates, and learns from execution feedback without labels (about +10 % on agent benchmarks). When a model rewrites the whole context, it shrinks to generic advice ("context collapse"). So a lesson is its own named entry with its own evidence, written and removed alone; nothing summarizes or rewrites the list.
- **An actionable procedure beats a remembered failure.** CODESKILL ([arXiv 2605.25430](https://arxiv.org/html/2605.25430)) and REM ([arXiv 2610.27377](https://arxiv.org/pdf/2610.27377)) find that short procedures carry over to later tasks better than raw trajectories. So a lesson is one sentence that says what to do ("run make e2e before saying done: unit tests miss the web client"), not a transcript and not a warning.
- **A memory bank goes stale and gets contaminated unless it is curated.** The survey of self-evolving coding agents ([arXiv 2608.03392](https://arxiv.org/html/2608.03392v2)) names the failures: stale, redundant, too repository-specific, learned from failed runs. So an agent only suggests a lesson and the owner takes it. The list is capped at 12. A suggested lesson is shown to agents that read the playbook, so they add to it rather than suggest it again. Remove is one press.
- **Nothing the agent writes reaches later agents without a person's gate.** Work on harness tampering ([arXiv 2609.00069](https://arxiv.org/pdf/2609.00069)) and the Thoughtworks Radar entry on self-improving harnesses agree: an agent must not be able to change, unchecked, what later agents are told. The owner's Take is that check.

(1) **The slot.** `lesson` is a seventh slot. Like a stage, it holds several entries, each with a name (`lesson:<name>`, lower case with dashes, the stage name's rule), up to 12 per project (`MaxLessons`). An entry is one sentence (`how`) with `evidence` and the thread it came from. A lesson takes no probe, address or deploy command.

(2) **An agent only suggests one.** An agent's `project.learn {slot: "lesson", name, how, evidence}` makes an entry with no text of its own and the agent's text as its `suggest`. A suggestion for an existing lesson goes beside it, also on a lesson the owner took or wrote. The owner's Take makes it the entry and the owner's (`by: owner`, for every slot now, so an agent's later finding waits beside it). Dismiss drops the suggestion, and a lesson that was only a suggestion with it. With `ownerAsked` (the owner's newest message asks for exactly this lesson) the lesson is the owner's at once, as any entry is. The owner's own lesson, added on the page, is theirs at once.

(3) **What agents are told.** The prompt's playbook lists the taken lessons after the other slots ("Lessons from earlier threads here, which the owner took; follow them:"); a suggested one is not in it. A project whose playbook holds only suggestions has no playbook in the prompt. The tool's read of the playbook also lists the suggested lessons, so an agent adds to one instead of suggesting it again. The prompt line every agent of a project gets says when to suggest one: when the owner corrects it on something every later thread here should do differently.

(4) **The page, the same on the desktop and the phone.** Lessons are listed after the notes, titled "Lesson <name>". A suggested one shows only its suggestion ("An agent suggests this lesson. Agents here are told it once you take it.") with Take it and Dismiss, and counts with what waits for the owner, so the group opens by itself. "Add an entry" offers Lesson with a name field until there are 12. The summary counts taken lessons ("2 lessons"). Removing a suggested lesson says the agent's suggestion is gone.

(5) **Linked projects.** Lessons travel with the playbook (V0.project-playbook (7)); a member takes up to 12 of them.

Not in this change (decision 0043): a retro that suggests lessons when a thread that went wrong settles; triggers read from facts (CI failed after done, a revert); counts of later threads that still failed in the same way, and doubt on a lesson that does not help; findings routed to the repository, to Fyr itself or to the setup.

Tests: `internal/core/playbook_test.go` (TestPlaybookLessons), `web/test/playbook.test.ts` ("a lesson is named and listed last; a suggested one waits for the owner").
