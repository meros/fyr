# V0.services-not-jobs: a dev stack, a dev server or a compose project is a service: its memory is reserved from its learned peak, the guard never freezes or names it, and a thread's containers count as its own

→ decision 0036 (D), slice 4; amends V0.164 (the detector and the roots of a freeze), V0.freeze-old-work (the elders), decision 0032 slice 2 (the parts of a turn) and decision 0029 S2 (admission). Builds on V0.job-limits.

The evidence (daemon.log, 19 Nov): the guard froze `docker compose -f devdocker/docker-compose.yaml --project-name acme-dev …`, whose containers held the memory in docker's own cgroups, outside `agents/`. It also froze `process-compose --config process-compose.yaml --tui=false` stacks of 3.6–4.4 GB that the same thread's e2e tests talked to.

(1) **What a service is.** A command that matches a service pattern. The built-in patterns are `process-compose` (`up`, `--config`, `-f`, or alone), `docker compose … up`, `docker-compose … up`, `npm`/`pnpm`/`bun run dev`, `yarn`/`pnpm dev`, `yarn run dev`, and `vite` (alone, `dev`, `serve`, `preview`). The config's `servicePatterns` adds to them. In Settings → Automation → Services (desktop and phone, one component), the owner removes a pattern, including a built-in one, or adds one (`host.servicePatterns` `{add}` or `{remove}`). The list is kept in the store. The patterns are matched against each process's command line in the thread's cgroup. The topmost matching process is the service and its subtree is its memory. The CLI's shell around a Bash command is never the service; its child is.

(2) **Containers.** fyrd reads the compose project from the command the way compose names it: `-p`/`--project-name`, then `COMPOSE_PROJECT_NAME=` in the command, then the directory of `--project-directory` or of the first `-f` file, then the folder. A thread's `docker compose … up` (with or without `-d`) makes the project the thread's. A `down`, `stop`, `kill` or `rm` of it ends that, and so does no container running for 2 minutes. The containers are found by the label `com.docker.compose.project` (`docker ps`, asked at most every 10 s and only while a thread has a compose project). Their memory is `memory.current` of `system.slice/docker-<id>.scope` (or `docker/<id>`). A thread whose containers hold at least the undeclared memory threshold's share of the agents' memory (8 %) is told so, at most once an hour, in the gate hook's context, with the `down` command.

(3) **Reserved, not undeclared.** Each service's reservation is its learned peak: a decaying max (48 h half-life, kept in the store) of what its processes and containers hold, and at least what they hold now. While the service runs, admission counts the reservation beside the held jobs and the undeclared work. The wait reason names it: "(Shop's services hold 4.1 GB)". The undeclared-work detector takes the services' memory in the thread's cgroup off the thread's working set, so a dev stack alone never flags a thread.

(4) **The guard.** A root whose subtree holds a service is neither a root nor an elder of a freeze. So the guard never freezes a service (a compose client included) and never names one as a part in a turn. `cgroup.Elders.Service` and `(*cgroup.Services).IsService(cmdline)` are the helpers the guard's other rules use.

(5) **The row.** A thread that runs services shows them after the rest of its line, on desktop and phone (`row-ui.tsx`): "service · 3.2 GB", or "2 services · 5.1 GB", counting what they hold now, containers included. GET /api/load gives each thread's `services` and the host's `servicePatterns`.

(6) **Limits.** Without cgroups (macOS) only the compose projects are followed. The processes there are not read, so a dev server can still be frozen. A pattern that matches too much (a commit message that says `npm run dev`) makes a short process a service for as long as it lives.

Tests: `internal/heavy/service_test.go`, `internal/cgroup/services_test.go` (TestSvc1–TestSvc5), `internal/admission/admission_test.go` (TestServicesAreReservedInAdmission), `internal/engine/lockorder_test.go`, `web/test/load.test.ts` ("a thread's services on its row"), `web/test/undeclared.test.ts` ("service patterns are added and removed").
