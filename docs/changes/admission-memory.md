# V0.admission-memory: the memory budget grows only when it is what holds a job back, admission keeps room for what the running jobs will still grow, and a class under three runs is sized like the prior

→ V0.163 (2) and (3), V0.job-limits (2) and (4), decision 0029 sections 2 and 3 (rule 3), decision 0036 (C).

(1) **The cause.** Three holes in how admission counts memory.
- V0.163 took the head's free memory as the smaller of the memory budget's free part and the real headroom above the reserve, and named the wait "memory" either way. On a calm host the AIMD controller grows the memory budget whenever memory holds the head back. So when memory outside the budget held the head back (the owner's browser), the budget climbed toward its ceiling of twice the host. That did not admit the head, and once the browser freed its memory, the budget admitted predicted peaks adding up to 200 % of the agents' memory.
- Decision 0029's rule 3 is `headroom − Σ (predicted peak − current) of running jobs − predicted peak(head) ≥ R_mem`. V0.163 dropped the running jobs' term and recorded no reason. A job admitted while it held 3 % of its 45 % predicted peak left the other 42 % looking free, and the next admission took it.
- A class's first run sets its learned peak directly, and V0.job-limits sized `memory.high` from any learned peak. So decision 0029's three-run rule (no lowering under the prior before three runs) did not apply to the limit. A first run that its unknown-class limit throttled taught a low peak, and the next limit held the next run lower still. An overrun of a class with no learned peak yet (its first run) raised nothing, so it was lost.

(2) **Two kinds of memory wait.** Admission now says which bound holds the head back: the memory budget (`memory`), or the host's real headroom (`headroom`), which covers the reserve rule and the headroom term of the free memory. AIMD grows the memory budget only for the first. For the second it does nothing, because a larger budget would not make the host's free memory larger. `GET /api/load` still sends `binding: "memory"` for both, so the fronts read the same two values. The engine reads the distinction from the snapshot (`Snapshot.Bound`).

(3) **The running jobs' growth.** Before admitting the head or backfilling a job, admission sums, over the jobs that hold a slot, their need's memory less what each grew since its grant: the predicted peak (or the prior for the self-deploy) less live growth, nothing for an idle hold, and all of it before the first reading. This sum comes off the headroom term, as rule 3 says. It is computed in the same pass as the holders' needs, under the pool's lock, from the job tracker's published readings. The wait says so: "needs ≈ 7.5 GB memory, 6.8 GB free (the running jobs may still grow 7.0 GB)". This keeps two jobs of unlearned classes (each the prior, half the host with the default `slots` of 2) from running side by side until the first has grown or ended. Rule 3 asks for that.

(4) **Sizing under three runs.** A class learned from under three runs is sized from at least the prior, as admission counts it (`slots.NeedOf`): memory 1/N of the agents' memory and CPU 1/N of their cores, N being the host's `slots` setting. Its learned peak and demand are used when they are larger. From the third run on, the learned values are used alone. The fix is in what `jobLimits` is given, not in the limit's unknown-class rule. A peak raise (an overrun of `memory.high`, or a kill for memory) on a class with no learned peak yet waits in memory for the peak the running job teaches, and raises that peak when the job ends.
