# V0.overload-retry: a run a passing provider failure stopped is Waiting, and Fyr retries it on a schedule

→ V0.quota-wait (a provider stop that is a wait), V0.quota-auto-continue (the automatic continue through the feed), V0.101 (Stopped on a failure), V0.185 and V0.203 (a wait is work going on), V0.21 (the end of a run). *Amends V0.21 (the end of a run that did not finish), and the row's Failed state for this one cause.*

A run that ended with "API Error: 529 Overloaded. This is a server-side issue, usually temporary — try again in a moment." showed as **Failed** in Needs you, red in the conversation, and waited for the owner to press Retry. The provider says itself that it passes; the owner can do nothing but press again later. That is a wait, as a quota stop is, and the pressing is Fyr's to do.

1. **The class.** A failure whose first line with words opens with the CLI's own "API Error" and names a status 5xx or 429, or (with no status) the words of a passing failure (overloaded, rate limit, connection error, timed out, …), is classed `overloaded` (`core.ClassOverloaded`, `core.OverloadNotice`). Another 4xx is a request the provider refuses every time and stays `api`. An out-of-quota notice is read first and stays `quota`. As with the quota notice, an agent that writes about such an error is not the error.
2. **The state.** `Attention` puts it in **Waiting** in Working, the reason "Waiting for the provider · retry 2 of 7 at 18:41" (the host's local time). It is not in Needs you, so no push is sent, it breaks no snooze, and it counts as work going on for "Snooze until work is done" and "Settle when done".
3. **The retry.** The clock (`NextCheck`, `KindClock`) retries at the failure's time plus the next wait of the schedule: 1, 2, 5, 10, 15, 30 and 30 min (the CLI has already retried for a short while itself). The retry clears the failure, sets Starting, records `overload.retried` and wakes the agent through the feed with a notice that says the last run stopped on a provider error and this is an automatic retry. A settled, archived, running or handing-over thread, or one with an open decision, is not retried.
4. **The end of the schedule.** A retried run that lasted 5 min or more before the provider failed again is a new incident and starts the schedule over. A run that ends any other way, or an owner move (a message, Retry, Dismiss, Settle), forgets the count. When the seventh retry fails too, that failure is classed `api`: Failed in Needs you and red in the conversation, the owner's as any failure. A thread unarchived after its retry came due shows the failure (as `api`) instead of starting a run nobody expects.
5. **The words.** Both fronts' rows read Waiting with the host's reason. The end of the run in the conversation says "Waiting to retry: <the error>" with the waiting mark, not "Failed (api): …" with the failed one, and it is not an outcome the owner acts on. A failure stored before this change keeps its class `api` and is not retried.
