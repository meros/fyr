# V0.guard-agents-stall: the agents' own critical memory stall makes memory short, and near oomd's limit the guard freezes the next thread without waiting a minute

→ decision 0036 (B) (act before oomd), (E4), decision 0029 S2 (memory guard), V0.load-tuning (2), V0.multi-freeze, V0.oomd-guard, V0.guard-wake.

(1) **The cause.** The guard decided "memory short" from the agents' headroom or the host's memory stall (`/proc/pressure/memory`). The agents' own stall (`fyr-agents.slice` `memory.pressure` full avg10) is what systemd-oomd compares against its limit, and it did not count. In decision 0032's incident the agents were at 53 % full while the desktop read 0.1 %, so the guard could stay "fine" while oomd moved toward a kill. Admission (decision 0029 S2) held new jobs on the host's stall alone in the same way. The AIMD budget (V0.load-tuning (2)) already read the agents' stall; the wake (V0.guard-wake) already waited for both stalls below elevated.

(2) **The agents' stall counts.** Memory is short when the agents' headroom is under the reserve, or the host's stall is critical, or the agents' stall is critical. The host's stall stays a trigger (V0.load-tuning (2) kept it: it is the rest of the host waiting for memory the agents hold, and freezing an agent is what gives it back). Admission holds the head with "the agents' memory stalls (critical)" when only the agents' stall is critical, and with "memory stalls near oomd's limit (55 % of 60 %)" in (3). The once-per-episode notice to the job that grew most, the freeze notice and the log say the same. Fine (for the wake) is unchanged: both stalls below elevated.

(3) **Near oomd's limit.** When fyrd knows oomd's limit on the unit (V0.oomd-guard) and the unit's full stall is within 10 points of it, memory is short, and the next freeze does not wait the minute (`AddFreezeAfter`) after the last one: oomd kills after its 20 s duration, sooner than a minute. While near the limit nothing wakes. The cap of the running threads less one, the oldest job and services are unchanged. The guard's log lines add `unit_full=… oomd_limit=…` when both are known. Where the limit reads as 0 (none, or unread) nothing changes.
