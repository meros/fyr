# V0.guard-wake: the guard holds a new heavy command before it freezes a running one, wakes frozen work by Buck2's rule, freezes up to the running threads less one, reacts to a PSI trigger, and says how long work was frozen

→ decision 0036 slice 5 ((E1), (E3)–(E6)), V0.151, V0.209, V0.multi-freeze, V0.oomd-guard. (owner, 19 Nov: "All slices please".)

(1) **Hold a start before freezing a run (E1).** While the memory guard says memory is short, the gate hook holds a newly matched heavy command. A command that has not started has no timer running, so holding it costs less than freezing a job that runs. The pool already queued a thread with no admission (memory short holds every job, decision 0029 S2). The hold now also covers a thread that already holds an admission and a learned command (V0.209: it never queues). The command is refused with "Heavy job (make e2e): memory is short on this host, so Fyr holds new heavy commands until it recovers instead of pausing ones that run. It did not run. Do not work around this. Fyr tells you in a [Fyr] message when memory has recovered; run the command again then. …" A subagent is told not to retry, as for a queued job. When memory is no longer short, each held thread gets "Memory has recovered on this host: run the heavy command Fyr held again." Log: `guard: held at the gate thread=… class=… admitted=… learned=…`.

(2) **Wake by Buck2's rule (E3).** The cap is the agents' memory when the host's or the agents' stall first went critical in the episode (`guard: wake cap agents=10.0 GB …`). The episode ends when memory is not short and nothing is frozen. The oldest freeze wakes first, at most one each 10 s, when the agents' memory plus the frozen thread's memory at its freeze is under the cap and both stalls have been below elevated for 30 s. Otherwise `guard: not waking thread=… yet: agents=8.0 GB + its 2.8 GB >= cap=10.0 GB`. Without a cap (the stall never went critical) the wake waits, as before, for 30 s of headroom at the reserve + 5 % and no elevated stall, now oldest first and one each 10 s. The thaws for "its processes are gone", "episode or hold ended" and the 10 min limit (V0.oomd-guard) stay. V0.multi-freeze thawed the newest first, one each 30 s.

(3) **More than one freeze (E4).** Up to the running threads less one are frozen at once (it was 3). The oldest running job is never frozen, even when it grew most (it was frozen then, V0.load-tuning), so one job always makes progress. A service is never frozen. Until the service class of decision 0036 (D) lands, the hook `GuardService` is nil and nothing counts as a service. Log: `guard: not freezing more: 2 frozen, at most 2 (running threads less one)`.

(4) **A PSI trigger (E5).** fyrd writes `full 150000 2000000` (150 ms of full stall in a 2 s window, the unprivileged form) to `agents/memory.pressure` and polls it for `POLLPRI`. Each event reads the load again and runs the guard at once, on the tick's goroutine. The 10 s tick stays as the fallback, and is all there is where the trigger is refused or there is no tree (macOS, a plain Linux without the cgroup tree). The start log says which: `guard: PSI trigger "full 150000 2000000" on the agents' memory.pressure`, or why not.

(5) **How long it was frozen (E6).** The thaw notice, which the thread's next hook output carries, names the time frozen: "Your heavy job runs again: Fyr thawed it. It was frozen for 4 min 12 s; a timeout or a slow step in that time came from the freeze, not from the work." The time is the cgroup's `frozen_usec` (`cgroup.stat.local`, present on this host's 7.3) since the freeze. Without it, or while the work takes turns, it is the wall time since the freeze. The thaw log line adds `frozen=`.
