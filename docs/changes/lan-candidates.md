# V0.lan-candidates: Settings → Hosts names each install found on the LAN, pairs it by its code or ignores it, flags one that claims a paired install's address or name, and real multicast is tested in a network namespace

→ #259, decision 0030 3.6, design/pairing/SPEC.md slice 4 ("Found, not paired"; Ignored), V0.159.

(1) **The row.** An install found on the LAN is one row per install id under Not paired, on the desktop and the phone (one panel, `web/src/peers-ui.tsx`). Its title is the name it announced (`fyr-<short id>`), and its line is the full id, every address it was heard at, and who found it: "found by mDNS" or "added by hand" (a fixed list). Tailnet discovery was retired (#360), so there is no third source. The row no longer prints the raw kind `lan`. On the phone the two buttons go under the text (`stack`), because two 44 px buttons do not fit beside it.

(2) **Pair.** The code comes from the found install: Pair binds the Add group to that install. The address is filled in, the invite field gets the focus, and a line says "Pairing with fyr-… : open an invite on that install and type it here". Add takes only an invite that names that id: an invite from another install is refused on the row before it is sent. The join itself is unchanged. Its link is pinned to the id in the code, so an install at that address with another key cannot answer.

(3) **A spoof or a duplicate.** The host marks a found install (`spoof`) that is heard at a paired install's address (host and peer port), or that goes by a paired install's name, host, or the short id a row shows. The row gets a red edge and a warning line, for example "This address is lab's (AX2C). Pair it only if you reinstalled lab. Pair asks for its code either way." Pair is never one press on such a row: it first asks "Pair anyway" or Cancel, and pairing then asks for the code as always. One id heard at two addresses (`dup`) is one row listing both, with "One id at 2 addresses: one install on two networks, or two machines with one id." The code decides there too, so Pair is not held back.

(4) **Ignore.** Ignore hides a found install from Not paired. The list is local to this install, in `ignored.json` in the data folder like `drive.json`, and is never part of the roster. It is set through `POST /api/front/peer/ignore {id, on}`, by a signed-in session. A member or this install cannot be ignored (a member is removed instead). "Show ignored (N)" under the group lists each ignored install with its date and where it is heard now, with **Stop ignoring**. `GET /api/front/peer/state` carries `ignored`.

(5) **Real multicast.** `TestTwoRespondersFindEachOtherInANetworkNamespace` (`internal/discovery/mdns_test.go`) runs the test binary again under `unshare -rn`, a user and network namespace that needs no root. The namespace gets a dummy interface `fyr0` with MULTICAST on, an address, and a route for 224.0.0.0/4. Two responders there must hear each other's answers over the kernel's multicast: id, address and instance name. Without `unshare` or `ip`, or where the user may not make the namespace, the test skips and says why. Inside the namespace, no answer is a failure. It passed here, 30 runs in a row. The manual check, for a host where the test skips: run `unshare -rn sh -c 'ip link add fyr0 type dummy && ip link set fyr0 multicast on up && ip addr add 10.77.0.1/24 dev fyr0 && ip route add 224.0.0.0/4 dev fyr0 && go test ./internal/discovery -run Namespace -v'` with `FYR_MDNS_NETNS=1` set. Or start two installs on one LAN with `discovery.mdns` on, and look for each under the other's Not paired.

Tests: `internal/peer/ignore_test.go` (one row per id with `dup`, a spoof by address, by name and by short id, Ignore across a restart and undone, a member or this install not ignorable), `internal/discovery/mdns_test.go` (the namespace test), `web/test/peers.test.ts` (the row's words, the warning lines, Pair asks on a spoof, the id an invite names), and the layout test's screen "settings found installs (#259)".
