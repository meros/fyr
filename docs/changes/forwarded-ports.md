# V0.forwarded-ports: a link to a server on the thread's host opens from any device, through a port of the front that has its own origin

→ V0.message-links-files (7) (the slice it left open), V0.51 and V0.54 (fronts and hosts), V0.129 (3) (the in-process link), V0.130 (the Serve socket), V0.156 (who acts on every hop), V0.176 (a thread's processes), decision 0030 3.2 and 3.5 (the browser's rules, the LAN listener), decision 0031. Amends V0.message-links-files (6) (the prompt line about a local server).

**Why.** An agent starts a dev server and writes `http://localhost:5173`. That address is the reader's own machine: on the phone, or for a thread on another host, it opens nothing, and the owner cannot try what the agent built without sitting at the host. The owner chose a forward over a screenshot only, the narrow rule for which ports, and the setup that publishes the ports.

(1) **Which ports.** Only a port that a process of the thread itself listens on. The host reads the thread's processes (its cgroup's; without cgroups its agent's descendants and the processes remembered as its own, as the leftover tracker does) and, on Linux, their listening sockets from `/proc/<pid>/fd` and `/proc/net/tcp`, `tcp6`; on a host without `/proc`, from `lsof`. A stolen session therefore reaches the servers the agents started and not a database, an admin page or Fyr's own loopback port. The host checks on every connection, so a forward ends with its server.

(2) **Why a port of its own.** A path under Fyr's address would run the server's pages with Fyr's origin: their scripts could call the API as the owner. A name per forward needs a wildcard certificate, which a tailnet name does not have. A port is a different origin under the same name and certificate. The front has a small pool (`forwardPorts`, default 7450 to 7453; `[]` forwards nothing). A link takes the port it already has, else a free one, else the one used longest ago.

(3) **The way of a connection.** The browser reaches the forward port; the front proxies each of its HTTP/1.1 connections to the host as one request, `POST /api/threads/{id}/forward/{port}`, whose body and answer both stay open: the bytes go both ways as on a socket. This is what the link between installs can carry: it is HTTP/2, which refuses an `Upgrade` request, so a WebSocket could not be proxied request by request; a connection as a stream carries it, and hot reload with it. The host route is exempt from the request deadline and from gzip. Over the in-process link (HTTP/1.1) the host turns on full duplex before it writes anything, an error answer included: found in the first test, where a refusal waited for the end of a body that has none.

(4) **What a forward port checks**, before anything reaches the server: the Host is this front's (the guard of V0.14, without the `X-Fyr` rule, which is Fyr's own API's); an `Origin` is this port's own; `Sec-Fetch-Site` is not `cross-site`; the browser has a session of this front, as its main port asks (in observe mode a request without one is served, as the front serves it; on the LAN listener never). `Fyr-Actor` and its kin are refused, a Tailscale header off Serve's socket too.

(5) **What the server sees and what comes back.** The server sees itself: `Host: localhost:<port>`, and an `Origin` and `Referer` of the forward rewritten to `http://localhost:<port>`, because a dev server refuses a Host it was not started for. Fyr's session cookie, `X-Fyr`, `X-Forwarded-*`, `Tailscale-*` and `Fyr-*` do not reach it; its own cookies and `Authorization` do. On the way back a redirect to its own address goes to the forward's, and a `Set-Cookie` of Fyr's session is dropped.

(6) **The shared cookie.** The ports of one name share their cookies, so the session travels to a forward port (that is how the port knows the owner) and the server's scripts run on a page of that name. What holds: the cookie is `HttpOnly`, so a script cannot read it; the front drops it before the server; Fyr's API refuses a call from a forward's origin three ways (the `Origin` check, `Sec-Fetch-Site`, and the preflight the `X-Fyr` header forces), which the browser tests of decision 0030 already hold. What does not: a script of the served page can write a cookie of that name and so sign the owner out of this browser. The served code is what the owner's own agent wrote and runs; this is accepted and written here.

(7) **The link.** In a thread's message, a link to `http://localhost:<port>/…` (also `127.0.0.1`, `[::1]`, `0.0.0.0`; in running text, as a markdown link or as code) keeps its text and points at `/forward/open?host=&thread=&port=&path=` on the front. That page makes the forward and redirects to it, so the link is an ordinary one on desktop and phone: it opens in a new tab, and its address can be copied and opened later, when it makes the forward again. A browser on the machine the server runs on (the front's own host, opened by a loopback name) is sent to the server itself. A refusal is a small page that says why: the port is not the thread's (and which are), the host does not answer, this Fyr forwards nothing. `https://localhost` is left alone: the forward speaks no TLS to the server.

(8) **The listeners and their setup.** Each forward port is served the three ways the front is: a loopback listener; a socket `serve-<port>.sock` for Tailscale Serve, with the rights of `serve.sock`; and with `tls` a port of the LAN listener (HTTP/1.1 only, which an upgrade needs). A port that cannot be opened is logged and left out. The setup's Phone step says when Fyr is on the tailnet and its forward ports are not, and its fix publishes each port to its socket; the NixOS module's tailnet unit does the same (`services.fyr.forwardPorts`). On macOS Serve cannot reach a socket, so a Mac's forward ports are loopback and LAN only.

(9) **The agent's prompt.** The line of V0.message-links-files now says: write a server you started as `http://localhost:<port>/<path>`, Fyr opens it from the owner's device for the ports this thread's processes listen on, keep the server running while the owner looks (`keep_process`); a screenshot is still the quickest way to show a page.

(10) **Not in this change.** A forward is not bound to the device that opened it: any signed-in device of the owner reaches it. A server that only speaks TLS, or one a process outside the thread runs (a server the owner started by hand), is not forwarded. The mock client has no front, so its link points at a name that goes nowhere.

(11) **Tests.** `internal/cgroup`: a thread's ports from the real `/proc` (this test's own process in a thread's cgroup, a listener and a client socket), from a written `/proc` (loopback and any-address listeners, not another address, an established socket or another process's), and from `lsof`'s output. `internal/server` `TestForwardCarriesAConnectionToAThreadsPortOnly`: two exchanges on one open connection over HTTP/1.1, the server's side closing when the browser's ends, and `404` for every port that is not the thread's. `internal/peerlink` `TestALinkCarriesATwoWayStream`: the same over the link between installs, in both directions. `internal/front`: a real server behind a forward through the in-process link (what it sees, a redirect and a cookie on the way back, a post without `X-Fyr`, an upgraded connection carried both ways), every refusal, the pool, the session in enforce mode, and the link's redirects. `internal/setup` and `cmd/fyrd`: the Phone step and its fix, the listeners and sockets. `web/test/filelinks.test.ts` and the layout test: what reads as a local URL, its mark, and the link's address on both fronts. Not tested against a running install: Tailscale Serve's entries for the new ports, and a real dev server's hot reload through a tailnet.
