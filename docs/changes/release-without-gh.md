# V0.release-without-gh: releases are read over plain HTTPS without gh, the release key is config, Settings → Updates shows both, and the Mac's launchd label names no account

→ decision 0027, V0.173, V0.update-changelog, V0.host-updates, V0.linux-without-nix, #200. The updater and both install scripts read releases with `gh`: an install needed a `gh` login even for a public repo, the key that verifies a release was compiled in (a fork had to patch the source to sign its own), nothing showed which repo and key a host trusts, and the Mac's launchd label named the upstream owner.

1. **No gh.** fyrd reads its release repo over HTTPS: the tag `deployable` with `git ls-remote` (no credential helper; no API call, as before), a release's five files from their public download URLs, and the compares (Contains, Behind, the changelog) and the tag fallback from GitHub's REST API. A public repo needs no login. The release it picks is unchanged: `deployable`'s commit and its release `build-<sha12>`.
2. **A token is optional.** `GH_TOKEN` or `GITHUB_TOKEN` (github.env), else `gh auth token` when gh is on PATH, is sent to the API only, never to the download URL: it raises the limit and reads a private fork, whose files (404 on the public URL) come from the API's asset endpoint with it.
3. **Rate limits.** An API answer with an ETag is asked for again with `If-None-Match` (the last 64 kept). A 403 or 429 that is GitHub's limit (`Retry-After`, or `x-ratelimit-remaining: 0` and its reset; a 429 without either: a minute) holds every API call until then, without a request. A 403 that is not the limit holds nothing.
4. **The key is config.** `updateKey` in config.json is the base64 ed25519 public key a release must be signed with; empty is the built-in key. fyrd logs the repo and the key's fingerprint at start, and says so when `updateKey` is not a key (every release would then fail to verify). `fyrrelease verify DIR [KEY]` takes a fork's key.
5. **Settings → Updates** shows the release repo and the key's fingerprint (`SHA256:` and the unpadded base64 of the key's SHA-256, as ssh-keygen prints) with "built in" or "updateKey", or the key's error as a bad row. It comes with `GET /api/updates` as `key: {fingerprint, builtIn, error?}` beside `repo`. One component on desktop and phone.
6. **Install scripts.** `install-linux.sh` and `install-macos.sh` read the tag with `git ls-remote` and the files with `curl`; neither needs nor checks a gh login (they note when gh is missing: the agents need it for pull requests). The first install checks the sums over HTTPS; fyrd checks every later release's signature.
7. **The Mac's label** is `app.fyr.fyrd`. An install or an uninstall stops the agents of `com.github.meros.fyr` and `com.github.meros.fyr.update` and removes their plists before it starts the new one, so a Mac that had the old label never runs two. Fyr.app (V0.mac-shell) takes over both labels at its first start (`macos/build.sh`'s `FYR_REPLACES`), and the script's `Fyr.app` it removes is the one whose bundle id is `app.fyr.fyrd.app`.
8. **Not changed:** the NixOS module (`nix/module.nix`) has no option for `updateKey` yet; a NixOS host sets it in the config the module writes once the module has one.
