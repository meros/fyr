# V0.playbook-probe-health: a stage says what its probe last answered, probes run several at a time, a probe can name the repository, and the page shows the path of a change

→ V0.project-playbook, V0.playbook-moments, 3.15. *Amends V0.project-playbook (3) (a probe may name `{repo}`), (4) (probes run four at a time, not one after another) and (8) (the page), and V0.playbook-moments (5) (a probe that cannot answer is said at once, not after two missed merges) and (6) (Remove asks first).*

Why, from the first probes the owner allowed on a live host: a project's two stages had a probe that waits for the deploy and sleeps 30 s between its looks, so every run was stopped at Fyr's 30 s limit. The host's log said `signal: killed`; the page said "Fyr runs this after each merge". Six merged changes were watched, so each pass took twelve limits, about six minutes, one probe after another, and the probe of another project that answers in under a second waited behind them. The probe compared the merge commit with one repository of a project that holds several, so a change of another repository could never be seen. The doubt of V0.playbook-moments would have said so two missed merges and a day later.

(1) **A probe's last answer.** A stage's entry carries `last` `{state, exit, note, at}`: `reached` (exit 0), `waiting` (another exit: not there yet), `timeout` (stopped at the limit) or `error` (it could not run: exit 126 or 127, or no folder), the last line it printed (200 characters), and since when it has answered so. The host writes it with `project.probed {id, name, probe, state, exit, note}` only when the state or the exit code differs from the entry's, so a probe each minute costs no write, and only for the command that ran. Several changes probed on one stage in a pass give one answer: a probe that cannot answer first, then that it saw a commit. Like `missed` it is the host's own and moves no stamp: a link's playbook that arrives keeps this host's `last` and `missed` for the same command, and drops them for another (it used to take the sender's). A probe written again with another command starts without them.

(2) **Broken.** A probe Fyr runs whose last answer is `timeout` or `error` is broken. The page counts it with what waits for the owner (the group opens, its summary says "1 probe fails"), and the agents' prompt says why with the last line, so the next agent in the project looks at it. The host logs the change of state once, not each run.

(3) **Several at a time.** A pass runs its due probes four at a time. A probe that sits until its limit holds back three others at most.

(4) **`{repo}`.** In a probe and in a deploy command `{repo}` is the pull request's repository, `owner/name`, checked to be one before it stands in the command. A command that names it for a change without one is not run (the probe's answer is `error`). A project of several repositories can so have one probe that tells them apart.

(5) **What an agent is told.** The prompt line, the tool `project_learn` and the brief of the run that learns a playbook say that a probe answers at once and never waits for a deploy (no `--wait`, no sleep), because Fyr runs it again each minute and stops it after 30 s, and name `{repo}`. The tool's read of a playbook gives each probe's last answer.

(6) **The page, the same on the desktop and the phone.** Over the entries stands the path of a merged change: Merge, then each stage in the order a change reaches it, with how Fyr follows it (probe runs, waits for your yes, probe fails, probe in doubt, no probe) and a mark on the live one; a stage goes to its entry. A stage's fields have their names over them (How a change gets here, Address, Probe, Deploy by hand), so a filled field still says what it is. Under a probe stands its state with a dot and since when: "Works: it last saw a change here 14:20", "Runs after each merge. Last answer since 14:20: not here yet (exit 1)", "Stopped at the 30 s limit since 18:35, so no change is seen here. A probe answers at once: it must not wait for the deploy.", "Cannot run (exit 127)"; with the last line it printed when it did not see the commit. Remove is a quiet control that asks first ("Remove Stage dev?"), because one press dropped an entry's text and commands.

Not in this change: a press that runs a probe once against a commit the owner names; a watch armed again for changes merged before a probe was allowed (a repository without GitHub deployments loses its watch at the first read while no probe is allowed, so the changes merged in the hours before the first yes are not probed); skipping a later stage's probe while the stage before it is not reached.

Tests: `internal/core/playbook_test.go` (TestProbeAnswerIsTheHosts, TestProbeStages), `internal/engine/playbook_test.go` (TestProbeAnswersAreKeptAndRunTogether), `web/test/playbook.test.ts`.
