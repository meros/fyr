# V0.quota-wait: a run the provider's quota stopped is Waiting for the reset, not a failure that needs the owner

→ V0.44 (the quota windows and their `ResetsAt`), V0.quota-reset-wake (the wake at a reset), V0.ci-wait-moves (a wait moves without the owner), V0.watch-waits (the wait reason on both fronts), V0.101 (Stopped on a failure), V0.143 (a reason names the host's local time), V0.21 (the end of a run), V0.185 and V0.203 (a wait is work going on). *Amends V0.21 (the end of a run that did not finish), and the row's Failed state for this one cause.*

A run that stops because the provider's quota is out showed as **Failed** in Needs you, with "Individual quota reached. Please upgrade your subscription…" on the card and a Retry that fails the same way at once. Nothing the owner says or does moves it before the reset, so it is not their move: it is a wait, as a wait for CI is.

1. **The class.** A failure whose text opens with the provider's own out-of-quota notice is classed `quota` (`core.ClassQuota`). The two CLIs say it differently and both are read: claude ends the run with an error whose text is the notice ("You've hit your weekly limit · resets 23 Nov, 4am"), agy ends it cleanly and writes the notice as the turn's last words ("⚠ Individual quota reached … Resets in 35m47s"). `core.QuotaNotice` reads only the first line with words, and only when it opens with the notice, so an agent that writes about the error it fixed is not the error. An interrupted run is the owner's Stop and is never a quota stop.
2. **The state.** `Attention` puts a quota stop in **Waiting** in Working, the reason "Waiting for quota · resets 18:41" (the host's local time, as V0.143's; "Waiting for quota" when the notice names no time). It is not in Needs you, so no push is sent for it and no question of it is asked. Past the reset the wait is over and the failure is the owner's again, as any failure (V0.101).
3. **The reset time** comes from the notice, never invented: "Resets in 35m47s" from the failure's own time, or "resets 23 Nov, 4am" (a zone in parentheses after it is the host's own) in the host's zone. A notice without a time leaves the thread Waiting until the owner moves it; nothing fires.
4. **The clock.** `NextCheck` re-reduces the thread at the reset, so the wait ends by itself, as a merge ask's wait for CI does. A quota stop counts as work going on for "Snooze until work is done" (V0.185) and "Settle when done" (V0.203) until that reset, and not after it: past the reset the failure is the owner's, so `NeedsOwnerAt`, `WorkGoingAt`, `WorkOverAt` and `WorkDoneAt` read it then, and a settle never fires on a thread the owner must look at.
5. **What ends it.** Retry, a message, or the wake thread.wakeOnQuota arms (V0.quota-reset-wake) clear the failure, as before; a quota stop is not a `NeedsOwner` failure, so it breaks no snooze.
6. **The words.** Both fronts' rows read the state word Waiting and the host's reason. The end of the run in the conversation says "Waiting for quota: <the notice>" with the waiting mark, not "Failed (quota): …" with the failed one, and it is not an outcome the owner acts on (it does not take the full weight of a failure's line).
