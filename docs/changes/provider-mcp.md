# V0.provider-mcp: Settings → Providers shows and manages each Claude provider's MCP servers

→ Amends V0.50 (3.16 Provider) and V0.53 (the login machinery is shared). The MCP servers a session starts with live in its CLI's own config, which Fyr never showed: to see why a server failed, add one, or sign in to one that needs OAuth, the owner had to open a terminal on the host with the right `CLAUDE_CONFIG_DIR` or token and run `claude mcp`. The CLI cannot do a sign-in without a terminal (`claude mcp login` refuses to run on pipes), so an agent could not do it for the owner either.

(1) **Where.** A provider's page has an **MCP servers** group after Projects, on the desktop and the phone alike (one component, `McpGroup` in `web/src/settings-providers.tsx`). It is there only when the provider's adapter implements `cli.MCPManager` (the claude adapter; agy has none), so the capability is the adapter's, not a check of its name.

(2) **The list.** `claude mcp list` (2.1.327) has no JSON output; `claudecli.ParseMCPList` reads its lines (`<name>: <url or command>[ (HTTP)|(SSE)] - ✔ Connected | ! Needs authentication | ✘ Failed to connect — <reason> | ⏸ Pending approval`). The scope is in no line: a claude.ai connector is named `claude.ai …`, a plugin's server `plugin:…`, and a server of the user config is in that file's `mcpServers` (read for the transport and the names of headers and env, never their values); anything else is `other`. The list health-checks every server and takes 10-30 s, so `provider.mcpList` starts it on a goroutine, ends it after 90 s, and the page shows the last answer with its time (Check now asks again). The page asks once when a provider's page opens and the host has no list yet. A change made while a list runs is followed by one more list, since the running one may have read the config before it.

(3) **The same config as the sessions.** Every `claude mcp` command runs with `Adapter.Env` of the provider's launch, as a session does: `CLAUDE_CONFIG_DIR` only for a provider with a folder of its own (a provider on the default folder must not set it: the CLI then reads `~/.claude/.claude.json` instead of `~/.claude.json`, found by checking), its login token as `CLAUDE_CODE_OAUTH_TOKEN`, its key and endpoint. fyrd's own credential variables are removed first (V0.agent-env), and so are the variables that mark a process inside a Claude Code session (`CLAUDECODE`, `CLAUDE_CODE_CHILD_SESSION`, …): with them the CLI refuses `add-json -` ("its permission prompt would not show the server"), which a fyrd started from an agent's shell would hit. The commands run in a private folder of their own (in the user's cache), so no project's local or `.mcp.json` servers mix in.

(4) **Shared configs.** Two providers that read the same config file (a default-folder login and a token login without a folder, or an endpoint without one) see the same servers and the same MCP sign-ins. The group says so: "Shared with <names>: they read the same ~/.claude.json, so a server added, removed or signed in to here changes there too." A claude.ai connector is the account's, so a token provider lists its own account's connectors and the list runs per provider.

(5) **Add.** Name, transport (HTTP, SSE, stdio), URL and headers or command, arguments and env. `provider.mcpAdd` adds it to the user config with `claude mcp add-json --scope user <name> -`; the JSON goes on stdin, so a header or env value is never in the process's arguments, a log line, a reply or a DTO. Names are letters, digits, `-`, `_` and `.`; a header name is a token and its value has no line break.

(6) **Remove.** Only a server of the last list, from the scope that list found (never the client's word). A plugin's server is refused ("goes away with the plugin") and so is a connector ("removed in claude.ai's connector settings"); the page offers Remove only where Fyr can remove it, after a confirmation.

(7) **Sign in and out.** `provider.mcpLogin` runs `claude mcp login --no-browser <name>` on a pseudo-terminal through the account login's machinery (V0.53, `startLoginProc`/`watchLogin`, generalised with a parser and a redactor per kind): the page shows the link and a field for the address the browser ends on (`http://localhost:<port>/callback?code=…&state=…`), `provider.mcpLoginCode` sends it to the CLI, `provider.mcpLoginCancel` ends it. A browser on the host completes it alone through the CLI's localhost callback. One sign-in runs per provider; it is done when the CLI exits 0, and the list runs again. `provider.mcpLogout` clears a server's stored sign-in. The code and state of a pasted address are redacted in every line Fyr keeps or shows (`RedactMCP`, which also hides secret-looking query parameters, flags, variables and bearer tokens in a server's URL or command line).

(8) **Never interrupts.** The list's answer, a sign-in's end and a relist only change the rows; the Add form, the sign-in field and their text stay as the owner left them. A sign-in panel opens only from the owner's Sign in.

(9) **Tests.** `internal/cli/claudecli/mcp_test.go` holds the parser to `claude mcp list` output with made-up servers, the environment and arguments of each command (per auth), the add JSON and its checks, the redaction and the sign-in's output. `internal/provider/mcp_test.go` runs every command against a fake `claude mcp` (the login tests' fake binary): shared configs, a token provider's own connectors, add with its header on stdin only, the refused removes, a wrong and a right redirect address, cancel, sign-out, remove, two adds in a row, a list that hangs, and that no header value or pasted code reaches the fake's arguments, a log line, a reply or a DTO. The web mock (`mock-providers.ts`) has the servers, and `layout.e2e.mjs` checks the group on the desktop and the phone.

(10) **Not in this change.** Local and project scope servers are not listed (the commands run outside any project); a server is added at user scope only; OAuth client id and secret (`--client-id`, `--client-secret`) are not offered.
