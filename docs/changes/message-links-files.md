# V0.message-links-files: a file path in an agent's message opens the file from the thread's host, a URL written as code is a link, and the agent is told what Fyr can open

→ V0.19 (markdown in the log), V0.34 (Copy), V0.54 (everything of a thread loads from its host), decision 0031 (the client names the host), V0.165 (the viewers). Amends V0.19 ("relative links mean nothing in the client": a relative link is now a file path or nothing).

**Why.** An agent's message names files and addresses all the time, and the owner could use almost none of them. A path (`internal/core/change.go:42`) was dead text: the file is on the thread's host, which is often not the machine the owner reads on, and never the phone. A URL inside inline code was not a link. A markdown link to a file was dropped to its text. The first slice of the link work makes what is on the thread's host openable from any front; the second (not in this change) makes a server on the host's loopback reachable.

(1) **Which files.** The owner chose the narrow rule: a file is served only from the thread's own folders. Those are the thread's folder, the worktree of each of its changes, and the temp folder (where agents keep scratch files). The file's real path, after symlinks, must lie inside one of them, so a link that leads out is not followed. The home folder and the folders above it never count, so a thread that runs in the home folder does not serve everything the owner has. Names that usually hold secrets are refused wherever they are: a file below `.git`, `.ssh`, `.gnupg` or `.aws`, and `.env`, `.env.<name>` (but not `.env.example`, `.sample`, `.template`, `.dist`), `.netrc`, `.npmrc`, `.pgpass`. A stolen browser session therefore reads the thread's working files, which the conversation already shows in part, and not the owner's keys. One answer, "no such file", covers every refusal, so the route says nothing about files it does not serve.

(2) **The host's routes** (`docs/API-v0.md`, "Files a message names"). `POST /api/threads/{id}/files/stat` takes up to 64 paths and names those that are served, with the real path, the size and the kind (text, image, other). `GET /api/threads/{id}/files?path=` serves one: text as `text/plain` (an HTML file too), every reply in a `sandbox` CSP with `nosniff`, so a file never runs as a page of Fyr's origin, and `no-store`, because a working file changes. Both go through `/api/h/<hostId>/…` like every host call, so they work for a thread on another host with nothing added to the front.

(3) **Which text is a path.** The renderer marks candidates and the host decides. A candidate is the whole text of an inline code span, or the target of a markdown link that is no URL, when it reads as a path: it starts with `/`, `~/`, `./` or `../`, or has a folder, or is a name with an extension that has a letter (`main.go`, not `v1.2`); no spaces, brackets or shell characters. A line after it is kept: `:12`, `:12:5`, `:12-20`, `#L12`. A wrong candidate costs one lookup and shows nothing, so the rule may be loose. A path in running text without code marks is not found: the cost of scanning every word of every message is not worth it while agents write paths as code, which (5) asks of them.

(4) **In the client.** The conversation asks the thread's host about a message's candidates (one call per message, 250 ms after the text stops changing, so a streaming message is not asked a character at a time) and keeps the answers per thread; "no such file" is kept 30 s, because an agent names a file a moment before it writes it. A path the host has is a link (the link colour, underlined, focusable, Enter opens it). A press opens:
   - **text** in the file viewer: the path in the header (the folder shortens, the name and line stay), line numbers, the named line marked and scrolled to the middle, Copy path (the real path on the host, to paste back to an agent), Download and Close; a file over 2 MB is offered as a download;
   - **an image** in the image viewer of V0.165, with its zoom and Download;
   - **anything else** as a note with Download.
   The viewer is one component for desktop and phone, mounted beside the image viewer, and is one history entry: Back, Escape and Close leave it. It uses the theme's colours, not the image viewer's black. The only difference between the fronts is the Copy button's height on a touch screen (a finger needs it), written next to its rule in `chrome.css`.

(5) **A URL written as code** (`` `https://example.com/x` ``) is a link that keeps its code look. A URL was already a link in running text and as a markdown link; in a code block it has the block's Copy button.

(6) **The agent's prompt** has one more line (`promptLinks`): write a file as its path in inline code, absolute or relative to the working folder, with `:line`, and not as a bare name that exists in several folders; write a URL in full and not only inside a code block; show a picture or a page with `show`; a server on the host is not reachable from the owner's device, so show a screenshot of it. The renderer does not depend on the line: it reduces misses.

(7) **Not in this change.**
   - **Forwarded ports.** The owner chose them for a server on the host's loopback: on a press the front proxies one of a small pool of its own ports to that port on the thread's host, behind the Fyr session. A path under Fyr's own origin is ruled out, because the served app's scripts would run with Fyr's origin and could call the API. Open before it is built: whether the link between installs carries a WebSocket upgrade (hot reload needs it), and that the forward shares the front's host name and so its cookies (the proxy must drop the Fyr session before it forwards, and the API's Origin check must hold against a proxied app). Until then a `localhost` URL in a message stays a plain link, and the prompt tells the agent to show a screenshot.
   - **A menu on a link** (Open, Copy) of Fyr's own. A web link has the browser's menu on both fronts; a file's path is copied from the viewer.
   - **Open in the editor** when the owner reads on the thread's host itself.

(8) **Tests.** `TestThreadFile` (`internal/hostfs`): the ways a path is written, a worktree's file, the temp folder, and every refusal (outside the folders, a symlink that leads out, the secret names, a folder, the home folder as a thread's folder). `TestThreadFiles` (`internal/server`): the stat reply, the limit, the headers that keep an HTML file from running, the download form and the 404s. `web/test/filelinks.test.ts`: what reads as a path and what does not, the line forms, the lookup's cache (one call for the same path asked twice, a failed call records nothing, "none" expires), and the markup the renderer writes for a code span, a link target and a URL in code. The layout test's `V0.message-links-files phone` and `desktop`: the paths the mock host has are links and the one it has not is text, the viewer shows the file's name and line in its header and the named line in view without a sideways scroll, Back leaves it, an image opens the image viewer and a binary file the note.

(9) **The mock's paths are behind `&files`.** The message that names them was first added to the mock thread that most layout checks open. The first CI run then failed one of them (the phone's Cancel on a waiting message: the tap did not cancel it), which passed in the full run on the development machine and 12 times of 12 alone beside four busy loops. No cause was shown; the message made that thread's conversation taller, so the thread is as it was and the paths show only with the flag.
