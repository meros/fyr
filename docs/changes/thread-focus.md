# V0.thread-focus: one thread is one topic, and Fyr tells a thread once when it grows past one

→ 5.12 (threads for agents), 5.14 (the agent feed), V0.22 (`thread_new`), V0.59 (`after` and `group` on a change).

Threads tended to grow into "master threads": a review turned into IAM fixes, then service-account work; a hotfix pivoted into a full investigation; a spec went on to a migration, a job, a UI and a back office in two repos; one thread held eight PRs across four repos. Such a thread is hard to read, its title stops saying what it is about, its many merges can break deploys that another thread depends on, and the owner cannot settle any part of it. One focused thread per topic reads, reviews and settles one thing at a time.

(1) **The agent prompt** (`internal/agent/prompts.go`, every setup) has a line after the threads line: one thread is one topic and about one PR, or one app change and its hosting change. Changes that belong together are one piece of work: a stack (`change_open` with `after`) or a group. When the work branches into a separate topic (another bug found, a pivot, a follow-up feature, an unrelated fix in another repo), the agent starts it with `thread_new` and a full brief (the goal, what it found, the repo and branch, links, what is done and what is left), tells the user, and goes on with its own topic. A spec, review or audit thread hands its implementation to new threads, one per topic.

(2) **The nudge.** After each reduce that adds a code change to the thread, Fyr joins the thread's changes into pieces of work: changes linked by `after` (either way) or sharing a `group` are one piece; an abandoned change is none. A change Fyr made from an observed push or PR counts like an opened one. When the new change is the first piece in a repo no other piece works in, while another piece has a repo, or when the thread now holds 3 pieces (`SplitAtPieces`: the topic, perhaps a follow-up fix, then a new topic), the `split` notice (urgency next) tells the agent which pieces there are and to start the other topics with `thread_new` and a full brief, or to tie a change that belongs with another by `after` or `group`. It is said once per thread (`splitNudged` on the thread); Fyr never splits, moves or refuses anything itself.

(3) **Light.** A stack, a group, an app and its hosting change in one group, and a second change in the same repo say nothing. The nudge is `next`: after the agent's own `change_open` it is `self` and goes out with the next tool call; after a change Fyr observed it reaches an idle agent like any `next` notice.
