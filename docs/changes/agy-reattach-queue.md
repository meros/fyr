# V0.agy-reattach-queue: reattaching an `agy` session restores its in-flight turn state and queued messages

→ amends V0.agy-adapter (1)–(2), V0.33, V0.90; `internal/cli`, `internal/cli/agycli`, `internal/agent`.

Unlike `claude`, which buffers queued follow-up messages inside the child CLI process, `agy` speaks ACP (`session/prompt` one turn at a time) and buffers follow-up messages in memory inside `fyrd`. When `fyrd` restarted and adopted a kept `agy` process mid-turn, the new `acpSession` started with an empty queue and `reattachActive = false`, while `t.Outbox` still held the queued messages. Those queued messages never ran after the in-flight turn finished, remained stuck as Waiting, and returned `"The agent has already read this message"` (409) when the owner tried to cancel them. In addition, a new message sent while the pre-restart turn was still running could be sent concurrently over ACP, and a queued message starting a follow-up turn after a `result` left `s.live` false until the model emitted a tool call or finished.

(1) **Reattach state (`internal/cli`, `internal/agent/runner.go`, `internal/cli/agycli`).** `SessionReattacher.ReattachSession` takes `cli.ReattachState{SessionID, Model, Running, Queued}`, populated from the thread's state and its `"queued"` `Outbox` entries. On reattach, `acpSession` restores `queue` from `Queued` and sets `reattachActive` from `Running`.

(2) **Ordered draining and cancellation (`internal/cli/agycli/acp.go`).** While `reattachActive` is true, `SendUser` queues new messages behind the restored queue and `promptWorker` waits instead of sending a concurrent `session/prompt`; `CancelMessage` withdraws any restored or newly queued message before it starts. When the pre-restart turn's JSON-RPC response arrives, `finishReattachedTurn` emits its `result` before clearing `reattachActive` and waking `promptWorker` to drain the queue.

(3) **Prompt response acking and follow-up turn start (`internal/cli/agycli/acp.go`, `internal/agent/turn.go`).** `acpSession` holds the runner sequence number of a `session/prompt` response unacked until Fyr handles its `result` message (so a restart before `RunEnded` persists replays the response cleanly). `Manager.handle` calls `turnStarted` on `command_lifecycle` `"started"` so a queued follow-up turn immediately enters the running state while the model thinks.
