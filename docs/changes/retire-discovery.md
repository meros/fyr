# V0.retire-discovery: the old tailnet discovery is gone; a front follows another install because it is paired, or because the config names it

→ V0.123, V0.125, V0.158, V0.160, V0.174, decision 0025, decision 0030 slice 5, #268. *Removes V0.123 (1) and (2) (the probe of the owner's tailnet nodes and of config `peers`, and the front following what it found); V0.123 (3)'s `found: true` now marks a host the roster brought. V0.123 (4), the loopback `hostListen`, and V0.51's whois listener stay, see (3). Amends V0.125's Hosts foot and origin row, see (6).* (owner, #268: "move peers.WellKnown into peer or discovery, then delete internal/peers, newDiscovery, AddHost(Found:true), oldListeners, the whois PeerHandler and restartWhenTailnet if nothing else needs it. Confirm installs that already have peer links keep working.")

(1) **Gone.** `internal/peers` (the discovery round every 60 s), fyrd's `newDiscovery`, and the front's `AddHost` from it. Config `peers` and the `-peers` flag are read only to log that they are ignored, so a config or unit that has them still starts. `tailnet.Candidates`, which only discovery used, is gone.

(2) **Moved.** The `/.well-known/fyr` answer (`WellKnown`, its handler, and `OnlyWellKnown` for the macOS Serve port) is in `internal/peer`, beside the pairing that reads it. It answers as before, `host` included, so an install of an older build still finds this one while both run.

(3) **Kept, and why.** The old host listeners (the whois listener of `hostListen`/`hostPort`, the loopback `hostListen`), `PeerHandler`, `restartWhenTailnet` and the front's whois fallback stay. A configured host (`hosts:` in the config, the NixOS module's `services.fyr.hosts`, `-hosts`) that is not paired reaches its host only through them: a role front always has such hosts, and the module's `peerPort` defaults to null, so an install with no peer port cannot pair at all. They still go away per install as before: the peer way in's enforce removes them (by hand, or by rule 3 once every followed host is on the pinned link), and `fyr auth observe peer` brings them back. Decision 0030 slice 5 removes them in code once every install enforces.

(4) **A paired install.** A host the roster brings is followed over its peer link only (`hosts[].found`, `link.via` "peer"). A configured host that is also paired gets the peer link on the same row (by its key id, else its name) and is reached over it; the whois link is used only when the peer link cannot be made, and that use is counted (`whoisLinkUses`) and keeps the peer way in observe.

(5) **The macOS installer** no longer sets `hostListen tailnet:7778` for a new config: the Mac pairs on its peer port. A `hostListen` an earlier run wrote stays.

(6) **Settings → Hosts**, one shared row on both fronts. The foot says "Your other installs join this list once they are paired; installs of your Tailscale login pair by themselves. A host that is not paired goes in fyrd's config (`hosts`)." A found host's origin row is "Paired: Fyr follows it over its peer link, as one of your installs. It leaves this list when it is removed from them." (was "Found on the tailnet … 30 days after its last answer").

(7) **On upgrade.** A front keeps no host that discovery alone found: it was followed while the front ran and never stored. So an install that a front followed only because discovery found it (not in `hosts:`, and not paired, e.g. a NixOS host with `hostPort` and the module's default `peerPort = null`, or an install of a build from before pairing) leaves that front's Hosts and inbox after the update. Before updating, give such an install a peer port (NixOS `services.fyr.peerPort`) so it pairs, or name it in the front's `hosts:`.
