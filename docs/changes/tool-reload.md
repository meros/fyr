# V0.tool-reload: an agent process that outlives an update reads the new build's tools without a restart

→ V0.90, V0.107, V0.143, V0.133, 16.2 (MCP binding). *Amends V0.107 (1)* ("the CLI reads the tool list once"). (#155: on 16 Nov a coordinator thread needed a tool from the new build in a running thread, tried `kill -TERM` on its own process, and the auto-mode classifier refused it. A process kept by the runner (V0.90) kept the tool list it read at start until it ended.)

(1) **The CLI reloads the tools itself.** Measured with Claude Code 2.1.322 against a test server: the CLI opens the streamable HTTP transport's server stream (GET, `Accept: text/event-stream`) after `initialize`, also without an `Mcp-Session-Id`. It runs `tools/list` again on each `notifications/tools/list_changed`. When the stream breaks it reconnects with backoff (in the tests, 4 s to 80 s; a 60 s outage of the server was survived), sends `initialize` and reads the list again. The next turn sees the new tools: in the test, turn 1 listed `tool_old` and turn 2, after the server was replaced, listed `tool_newbuild`. No restart was needed.

(2) **Fyr's MCP server keeps the stream.** `/mcp` answers a GET with `Accept: text/event-stream` (same bearer token, same Origin rule as a POST) with an SSE stream. The stream sends one `notifications/tools/list_changed` when it opens and a comment line every 25 s after that, and stays open until the client leaves or fyrd stops. `initialize` offers `tools.listChanged`. fyrd ends the streams before it shuts down, so each CLI connects to the next fyrd and reads that build's tools. Before this change, a GET was 405 and the CLI had no stream to lose.

(3) **The hash.** The server hashes its listed tools (names, descriptions and schemas, sorted; hidden aliases left out) into 16 hex characters. A token counts as current when it read `tools/list` from this fyrd with this hash, or holds a server stream open. Each process records the hash of the build that started it in its runner note (`tools`). A process from before this change has no hash.

(4) **The fallback: replaced at its next idle point.** An adopted process whose hash differs from this build's gets 5 minutes to read the new tools itself (the CLI's reconnect backoff). If it has not, Fyr ends it the way a view refresh does (V0.37, V0.133): at once when it is idle, otherwise when its turn ends and no background task, question or unread message is left. A turn is never cut for this. The next message resumes the same session (`--resume`), with the new tools. When the process ends, the thread gets one line: "Fyr restarted this agent's process to load the new tools (build <id>)" (`agent.restarted`, the same row as a watchdog restart on both fronts). This covers the processes that are running when this change is deployed, since they never opened a stream, and any CLI that does not reconnect.

(5) **No `process_restart` tool.** While the MCP connection works, the stream gives the CLI the current list, so an agent never has old tools and a working connection at the same time. When the connection is gone, a tool that asks for a restart cannot be called either. The owner's Restart (V0.143) stays for anything else. So no agent needs `kill` for this.

(6) **Where it lives (decision 0035).** The stream and the hash are MCP, in `internal/mcp`. The note, the idle point and the resume are in the agent runner (`internal/agent`). The core and the client get nothing new.

Tests: `TestStreamSendsListChanged`, `TestToolHash` (internal/mcp); `TestMCPStreamThroughTheMainPort` (the stream passes the guard, the deadlines and gzip unbuffered); `TestToolReloadReplacesAtIdlePoint` (two processes kept across an update that changes the hash, one idle and one in a turn: the idle one ends at once, the other only after its turn, each thread gets one line, and each resumes its session), `TestToolReloadLeavesCurrentProcesses` (a process that read the new tools, and one started with the same tools, keep running).
