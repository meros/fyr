# V0.forget-front: the client does not know which front it is connected through, except where Settings says so

→ decision 0031 slice 4 (2.6, C8, C9, C10, tests 1 and 8), V0.51, V0.54, V0.125, V0.126, V0.132, V0.170, V0.client-refs. *Amends V0.125 (no Hosts row is tagged "This install"; a front that lists no hosts shows none), V0.126 (no per-host group's line is "This install"), V0.132 (the host picker has no "(this install)").* (owner, 17 Nov, decision 0031 Q3: "Only in Settings"; 19 Nov: "Finish decision 0031".)

(1) **One place.** Settings → This device has a row **Connected through** with the front's name. Nothing else names the front: the host pickers (New thread, New project) list the hosts by name in the owner's order, an offline one marked; Settings → Hosts has no "This install" tag on a host row (the Paired installs panel still marks the install whose roster it shows, which signs its pairings: decision 0031 2.9 keeps the roster as it is); the per-host groups of Providers and Automation say online or offline since when, for every host alike; the Hosts summary with one host is "One host".

(2) **The connection is the browser's.** The desktop rail's foot and the phone's header say **Connected**, **Connecting…** or **Offline**, with "Connected to Fyr" and "Fyr is not reachable, retrying" as their tooltips; the phone's strip says "Reconnecting…", an offline Settings page "No connection to Fyr". Whether a host is reachable is that host's own line.

(3) **No self fallbacks.** A record's host is the host whose state it came in: a thread that names none belongs to no host the filter can turn off, and is not taken for the front's. The host marks read a host's machine from the host list only; a front lists its own host there like any other. Settings → Hosts lists exactly the front's hosts. The route "this machine" is the host whose link is the pipe (or a loopback URL), a fact about the link.

(4) **The update banner.** It is the update of the host the front runs in (V0.39: that is the update that drops the connection), and **Restart now** names that host by the id the update came with, not the front's.

(5) **The approval card on the phone** says "on <the thread's host>", not the front's name.

(6) **Found by the neutrality test, fixed here.** (a) A folder preview's page is a sandboxed frame with no origin, so the browser says the requests for its own files are cross-site (a module script's `Origin` is `null`); the front's browser rules refused them, and a preview that loads its own script showed nothing. A `GET` of a preview's page or file now passes those rules, as it already passed sign-in: it carries no cookie, changes nothing, and the 80-bit id in its URL is its key (V0.19, V0.47). Every other cross-site `/api/` call is still refused. (b) Settings → Hosts crashed when the front had no pairing candidates: it sent `candidates: null`. The front sends a list, and the client reads a missing list as empty. (c) A page the browser keeps in its back/forward cache kept its stream open; after a few such pages the browser's six connections to the front were used and the next page stayed "Connecting…". The client closes its stream when the page is hidden for good and opens it again if the page comes back.

(7) **Tests.** A guard over the client's sources: only Settings, the banner, the build check and the modules that read the state touch the front's identity, no label says "(this install)", and the self fallbacks are gone. The layout test (desktop and phone): two hosts with one thread id are two rows, each with its own host, each opened by its ref; no picker, Hosts row or host group says "this install"; one host shows no host on the rows; This device names the front. The browser neutrality test (`web/test/neutral.e2e.mjs`, decision 0031 test 1): two paired scratch fyrds, one script through each front in Chrome (the hosts, a project and a thread with an attachment on each, the inbox, each thread, a folder preview of each host that loads its own file, a settings page, the Hosts page, the host order, a restart of the front in the middle and the previews again); the two runs must show the same.
