# V0.project-playbook: a project keeps a playbook of what happens around and after a pull request; agents learn it, the owner corrects it, and Fyr runs each stage's probe itself after a merge

→ 3.15, 5.12, V0.66, V0.116, V0.linked-values-sync, V0.prompt-fits-setup, decision 0034. *Amends V0.66 (3) (a non-production deployment's address is kept as evidence too; a repo without any deployment keeps its watch when the project has stage probes).*

Why: Fyr's hard workflow ends at the merge. A change goes working, review, landed, live, and live is read only from GitHub Deployments, so a repository that deploys another way (a release tag, a self-update, a manual command) stays at landed. What happens around the pull request (which environments follow a merge and when a change can be tested there, how a change is verified, where an issue is filed) lives in `CLAUDE.md` or in nobody's notes: an agent can read prose, Fyr cannot act on it, and where it is missing each thread works it out again or asks the owner.

(1) **The playbook.** A project record carries `playbook`, a list of entries in fixed slots, and `playbookAt`, its stamp. The slots: `stage` (an environment a merged change reaches, named: dev, prod), `verify`, `promote`, `issue`, `run`, `rollback`. A stage may carry `url` (where it is looked at), `probe` and `live` (reaching it makes a change live; a stage named prod or production is live without it). At most six stages and one entry in each other slot, each a sentence or two (`how`, 600 characters), with who wrote it (`by`), the thread it was learned in and what it rests on (`evidence`). It is not a second memory beside `CLAUDE.md`: it holds what Fyr itself uses, and what is the owner's and not the repository's.

(2) **Writing.** `project.learn {id, slot, name?, how?, url?, probe?, live?, evidence?, thread?}` writes one entry whole; `{…, remove: true}` removes it. An entry the owner wrote is kept against an agent (the rights row `project.playbook`): the agent is refused and tells the owner what it found. The tool `project_learn` is the agent's way in, and without `slot` it reads the playbook. With `ownerAsked` (the newest message is the owner's own, as in `project_setup`) the entry is the owner's.

(3) **A probe is a script, and it needs the owner's yes.** A stage's probe is a shell command where `{sha}` is the merge commit; exit 0 says the stage holds that commit. Fyr runs it by itself, so nothing asks a model where a change is. Because an agent may write it and Fyr runs it unattended, it runs only once the owner allowed it: `project.learn {id, slot: "stage", name, allow: true}`, owner only (the switch on the project's page, or `ownerAsked`). The yes is for one command: an entry written again with another probe waits again. The commit id is checked to be hex before it stands in the command.

(4) **Stages after a merge.** While a merged change's deploy watch is armed (V0.66), the host runs each allowed probe of the thread's project that the change has not passed, in the project's folder and its environment (as a Run card), with a 30 s limit: each minute in the watch's first hour, every 10 minutes in its first day, then every 30. A probe that exits 0 is an observation of the deploy observer, the same Input as a GitHub deployment: the condition `deploy:<stage>` is ok, the stage's `url` is evidence, and a live stage moves the change to `live`. A probe that does not exit 0 writes nothing. A repository without any GitHub deployment used to lose its watch at the first read; with stage probes it keeps it and GitHub is not read again (`observe.noRemote`). The watch's limits are V0.66's: 24 hours without a stage reached, 7 days with one. A settled thread keeps its watch, so a merged change stays on its thread and is not moved elsewhere.

(5) **The agent.** Every agent of a project gets one line saying when to record an entry, and the playbook itself, in its prompt (read when its process starts). A stage reached is the fact notice it already was, now with the address: `Deploy to dev (https://dev.example.com) on PR #12: succeeded`. It rides with the next message and wakes nothing. An agent that must act at that moment (verify there, tell the owner it can be tested) arms a watch on the condition `deploy:<stage>`, which the watch tool already takes.

(6) **Learning from the repository.** `project.playbookRun {id}` starts a thread in the project's folder whose brief is to read the workflows, deploy scripts and docs, and what followed the last merges, and to record what it can back with evidence. It asks nothing and changes nothing; its probes wait for the owner's yes like any other.

(7) **Linked projects.** A link's members take the playbook with the newest `playbookAt` whole, the owner's yes included: the front sends `project.sharedPlaybook {id, link, at, playbook}` to each online member with an older stamp, as it sends the image (V0.linked-values-sync), from its own copy of the source's record, so the source's host need not be online. A member that was offline catches up when it is back; a host from before this change answers unknown action and is tried again.

(8) **The client, the same on the desktop and the phone.** A project's page has a folded group Playbook: each entry with its text to correct, a stage's address and probe, the switch that allows the probe, Remove, and "Learn from the repository". Its summary names the probes that wait for the owner, and it opens by itself while one does. An edit goes to one record (this host's, else the first online member). A merged change shows where it is among the stages ("on dev · prod next") on its card and on its row under "Done here"; a reached stage with an address is a link.

Not in this change: a stage reached does not put a thread in Your move by itself (the agent's watch and its question do that); a manual promotion as a Run card offered when the stage before it is reached; marking an entry doubtful when its probe never succeeds; an agent's finding that contradicts the owner's entry shown as a suggestion on the page; adding an entry by hand on the page (an agent writes it, the owner corrects it).
