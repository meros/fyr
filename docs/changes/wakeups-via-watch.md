# V0.wakeups-via-watch: an agent's wake-up is Fyr's timed watch, the CLI's own timers are off, and the owner sees the wake-up on the thread and its row and can cancel it

→ V0.12 (the prompt, the launch), V0.133 (its "not covered"), V0.7 (the idle stop), #46 (the agent's watches), V0.203 (the settle-when chip it looks like). Claude Code has in-process timers (CronCreate, CronDelete, ScheduleWakeup). They live in the CLI's process, and Fyr ends an idle process after 10 minutes (V0.7), so a wake-up an agent set hours ahead died with it and nobody saw it go. V0.133 listed this as not covered. Fyr's own watch on a time (`mcp__fyr__watch {when: {kind: "at"}}`, #46) is kept in the thread record and survives a stopped process and a restart of fyrd, so it is now the only snooze.

1. **The launch.** A process started with Fyr's tools gets `--disallowedTools CronCreate,CronDelete,ScheduleWakeup`. A process without Fyr's tools keeps them: it has no watch to use instead. **/loop keeps them:** /loop is built on these timers. When the owner sends a message that starts with `/loop`, Fyr marks the thread, and an idle process without the timers ends first, so the /loop starts on a process that has them (sent during a run, it runs on the old process and the next process has them). The mark is in fyrd's memory and in the runner's note of the process (`timers`), so an adopted process keeps what it started with; a fyrd restart forgets the mark for a process it starts later, which is as well, since a /loop's timers did not outlive that process either.
2. **The prompt** (V0.12): a wake-up, a reminder or "check back at T" is `mcp__fyr__watch {when: {kind: "at", at}, then: "notify", note: <the prompt to run then>}`; Fyr keeps it while the process is stopped, wakes the agent at T with the note and shows it on the thread; the CLI's timers are off because they die when Fyr stops an idle session.
3. **Shown.** The thread carries `wakes` (`[{rule, at, note}]`, soonest first): the agent's armed watches on a time with then notify. One component, `web/src/wake-ui.tsx`, shows the soonest as a chip with a clock icon, "wakes 06:00 · <first line of its prompt>" in the owner's local time, with the date when it is not today ("wakes 21 Nov 06:00 · …"); its title holds the whole prompt and how many more are armed. It stands
   - in the desktop thread header, in the slot and style of the "settles when …" chip, after it;
   - in the phone thread header, right of the scrolling chips, in its own 44 px tap target (as the project chip), since the chips row is one button that opens Details. The phone header now also shows the "settles when …" chip, which only the desktop showed;
   - on the inbox row (`web/src/row-ui.tsx`, both fronts), so a thread that waits on a timer reads apart from a finished one. On the row it only shows: a tap on a row opens the thread, and on the phone a row swipes, so a cancel there would be too easy to hit by mistake.
4. **Cancel.** A press on the header chip, on either front, is the owner's `thread.cancelWake {rule}` (no rule: the soonest; off with "No wake-up is set"). It drops that watch, and the agent gets one `[Fyr]` notice that the owner cancelled the wake-up (its id, time and note) and not to set it again unless the owner asks. A wake-up that fires is gone without that notice.
