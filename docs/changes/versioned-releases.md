# V0.versioned-releases: a release can be a version vX.Y.Z, and an install follows the stable or the main channel

→ decision 0027, V0.release-without-gh, V0.host-updates, V0.update-changelog, #447. Releases were named `build-<sha12>` only: nothing told a user which build was meant to be stable, and every install followed every green commit of main.

1. **A version release.** A pushed tag `vX.Y.Z` (or `gh workflow run test.yml -f version=vX.Y.Z [-f commit=SHA]`) runs main's gate on that commit (`test.yml`, the self-hosted runner) and publishes the release `vX.Y.Z`: `scripts/release.sh` with `FYR_VERSION` builds the commit again with the version in both binaries (`-X main.version`) and in the signed manifest (`version`), signs it like a build release, and writes the commits since the previous version as its notes (for a stable version the previous stable one). It is rebuilt rather than copied from `build-<sha12>`: the binary must know its version, the manifest that names it is signed, and a build release is pruned after 30 newer ones. Only a commit on main is released; a dispatch never moves an existing tag. `deployable` and the build releases are not touched.
2. **Prereleases.** A version with a suffix (`v1.0.0-rc.1`) is published as a GitHub prerelease, not latest. The stable channel passes it over; an install pinned to it follows it.
3. **The channel** is `updateChannel` in config.json, read at start: `main` follows `deployable` and its build releases (unchanged; a config without the key is `main`, so existing hosts do not move), `stable` the newest published version that is neither a prerelease nor a draft (one API call to the release list per check, asked again with its ETag), a version `vX.Y.Z` pins the host to that release. A value that is none of these follows main and is logged at start. The commit the channel points at goes through the same watcher, quiet period, smoke test and rollback as before; its files come from the version's release, whose signed manifest must name that version.
4. **Switching** to stable on a host that runs a newer main build takes it back to the newest version at the next check: the channel's commit moved to an ancestor of what the host last saw, which the watcher follows as it follows `deployable` moved back (#153). The smoke test on a copy of the data runs first; a version that cannot open it is held back as any failed release is.
5. **The version is shown.** `fyrd --version` prints `fyrd v1.0.0 (build <sha12>)`, or `fyrd <sha12> (main)` on a build of main; `fyr --version` prints the launcher's and asks the current build. `fyrd version` (the smoke test's) is unchanged. A host's update state (`GET /api/state` `update`, the stream's `update`, `GET /api/updates`) adds `version` and `channel`. Settings → Updates says "Fyr runs v1.0.0 (build …) · stable channel"; a host's Updates group's Runs row names both; the status screen's foot names each host's version and channel. One component on both fronts.
6. **The install scripts** take `--channel stable|main|vX.Y.Z` and `--version vX.Y.Z`. A new install (no config) writes `updateChannel: stable` and installs the newest published stable version; an existing config keeps its channel; `--version` installs that version and, without `--channel`, pins to it. `install-macos.sh` gains `--print`, which says what it would install and changes nothing. Tests: `scripts` TestInstallLinuxChannel, TestInstallLinuxBadChannel, TestInstallMacosChannelPrint.
7. **Tests:** `internal/deploy` TestChannelStablePicksNewestVersion (newest non-prerelease, non-draft v*, build releases passed over), TestChannelMainUnchanged, TestChannelPinned, TestChannelRefusesAMislabelledVersion, TestChannelStableWithoutVersions, TestStableInstallAndSummary, TestParseChannel; `internal/release` TestParseVersionAndOrder; `cmd/fyrd` TestVersionLine; `cmd/fyr` TestVersionLines; web `updates.test.ts`.
8. **Not changed:** the NixOS module (`nix/module.nix`) has no option for `updateChannel` yet; a NixOS host follows main until it has one.
