# V0.command-effects-flake: the command-effects fixture records each path up to the upsert of the thread as it rests, so it is the same on every run

→ V0.mock-contract (#457, the fixture and the web test that holds the mock to it), V0.fix-flakes (the same kind of cause: a test that waited for one step and read the result of a later one).

`make test` regenerates `web/test/fixtures/command-effects.json` from `TestCommandEffectsFixture`, and `web/test/mock-contract.test.ts` then asserts the mock against it. The paths of the two commands that start work (`answer`, `run a Run card`) sometimes ended at `working` and sometimes went on to `done`/`seen`. The fixture on main had lost that last step (it was recorded on a run where the test was faster than the stream), so the web test, whose mock does end the agent's turn at `done`/`seen`, failed against it.

(1) **The cause: the test read the engine's state and then the stream, and the stream is a step behind.** `Engine.Apply` commits a change under `e.mu` and `publish` sends its upsert after, without the lock. The test waited until the thread read as idle (`h.wait`, a 20 ms poll on the engine's state), then unsubscribed at once and kept only the frames already in the channel. When the poll read the thread between the commit of the run's end and the send of its upsert, the last upsert (`done`/`seen`) never reached the recorded path. Whether it did depended on scheduling, not on the engine. The product order is right (a client reads the upsert when it is sent). The test was wrong.

(2) **The fix.** After the wait, the test reads the thread's current rev (`dtoOf(...).Rev`) and keeps reading the stream until an upsert with that rev arrives (up to 8 s, else it fails). It records only upserts after the thread before the command and up to that rev, so a later clock tick cannot add a step either. Each path now ends where the engine rests, and the regenerated fixture ends both paths at `done`/`seen`, which is what the mock sends.

(3) **Numbers.** Before: one plain `go test -run TestCommandEffectsFixture` on the laptop already wrote a fixture that differed from main's (the extra `done`/`seen` on both paths), and the web test failed 2 of 26 against main's fixture. After: the test binary was run 50 times beside 8 busy loops, and every fixture it wrote was byte-identical. `-count=50` under the same load passed. The web test passes 26 of 26 against the new fixture.
